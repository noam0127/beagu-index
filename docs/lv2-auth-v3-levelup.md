# 배구지수 회원·레벨업 정책 v3 — 레벨0부터 계정, 두 단계 승급

결정일: 2026-11-19  
상태: **최신 확정 정책 / 구현 전 / 운영 미반영**  
대상: Draft PR #49, branch \`feature/lv2-referral-phase1-20261119\`  
본 문서는 [v2 이전 계획](lv2-auth-v2-design-and-phase2-plan.md)을 전면 대체한다. Google Forms·Apps Script 1차 설치는 그대로 진행한다.

## 0. 챌린지는 별도 서비스로 보존 · 인디스쿨 공유 정책

[챌린지 독립 보존 및 인디스쿨 공유 정책·UX 조사](challenge-share-indischool-guidance.md)가 이 문서의 일부입니다.

- `/challenge.html` 경로, 기존 **참여 순번·인증서 PNG·과거 고유번호 발급 기록**은 보존합니다. 챌린지 화면에 들어가지 않아도 Lv0→Lv1→Lv2 승급이 가능해야 합니다.
- 챌린지 화면은 **타인에게 참여 인증서를 보여 주고, 인증 이미지를 저장하고, 챌린지 페이지 자체를 공유하는 기능**만 담당합니다. 기존 브랜치의 챌린지 추천 카드/고유번호 기반 `enroll` 호출은 제거했습니다.
- **내 계정의 Lv2 전용 설문 링크**는 로그인된 Lv1 계정의 `레벨업하기`에서만 발급합니다. 챌린지 페이지에서 발급하거나 챌린지 캡처에 삽입하지 않습니다.
- 공유 UX: `링크 복사`, `공유하기`(브라우저 OS 공유 지원 시), `인디스쿨용 글 복사`(개인 링크+혜택 공개+상단 [광고] 안내)로 구성합니다. UI는 신규 계정 체계 개발 때 구현합니다.
- **인디스쿨 쫑알쫑알(라운지)에는 개인 서비스/링크 홍보를 금지**한다는 공식 게시판 규칙이 있습니다. 홍보 가능한 `커뮤니티 > 함께해요` 게시판의 [광고] 표기·주 1건 제한을 안내하고, 인디스쿨에 자동으로 게시하는 버튼은 만들지 않습니다.
- 기존 챌린지 발급 API의 UUID-only 타인 원문 고유번호 조회 취약점은 **여전히 별도 패치 필요**. 독립 챌린지의 가시성·인증 정책을 임의 완화하지 않습니다.

## 1. 최종 UX

**회원가입/로그인은 레벨0부터 가능하다.** 로그인과 레벨은 별개다. 회원가입은 자동 승급이 아니다.

1. **Lv.0**: 비회원도 기존 무료 기능 이용. 로그인·회원가입 버튼 제공. 로그인해도 아직 Lv.0이면 Lv.0 권한.
2. 모든 페이지 공통 상단에 현재 레벨 표시 및 **레벨업하기** 진입점(로그인과 별도).
3. **Lv.0 → Lv.1**: 레벨업하기에서 기존 **공통 인증번호** 입력. 서버가 기존 Lv.1 인증 절차·시도 제한을 그대로 실행. 로그인 계정이라면 *검증된 Lv.1 자격*을 계정에 귀속(원자적, 서버 검증). 로그인하지 않은 사람은 기존 간편 Lv.1 이용을 계속 허용하되, 나중에 계정에 귀속할 때는 현재 유효한 서버측 Lv.1 인증이 필요.
4. **Lv.1 → Lv.2**: 레벨업하기에서 **나의 전용 추천 링크 발급/복사**. 계정 없이 Lv.1을 사용 중이면 먼저 회원가입/로그인을 안내. 로그인·이메일 확인이 완료된 계정에 서버가 불투명한 개인 추천 토큰을 **계정당 하나** 발급.
5. 추천받은 다른 선생님은 링크에서 기존 **공식 Google Form**을 제출. 유효한 제출 1건이 Supabase 서버의 해당 **계정** 추천 프로필에 연결되어 access_level=2로 자동 승급.
6. 레벨2도 동일 계정으로 PC·스마트폰 등 모든 기기에서 이용한다. 같은 기기만의 승급, 고유번호 입력, 챌린지 접근, 기기 UUID 본인확인은 필요하지 않다.
7. 이미 Lv.2인 사용자는 레벨업하기 대신 **레벨2 이용 중** 상태를 보여주고 관련 기능으로 연결. 로그인하지 않았다면 로그인 CTA.
8. **코드 기반 로그인 폐기**: 기존 고유번호(긴/짧은/10자리) 전부 기존 발급 데이터만 보존. 계정 생성·로그인·추천/승급에 이용 금지. 챌린지 화면은 Lv.2 동선과 완전히 분리한다.

### 레벨업하기 모달 (실행 규칙)

| 상태 | 주요 화면 | 주요 버튼 |
| --- | --- | --- |
| 비회원 Lv.0 | 레벨1이 되려면 공통 인증번호 입력 | \`레벨1 인증하기\` + 선택 \`회원가입/로그인\` |
| 계정 로그인 Lv.0 | 공통 인증번호 입력 | \`레벨1 인증하기\` |
| Lv.1 비회원 | 동료 추천으로 Lv.2; 발급에 계정 필요 | \`계정 만들기\` / \`로그인\` |
| Lv.1 회원, 이메일 미확인 | 이메일 인증 후 추천 링크 발급 | \`인증 이메일 다시 보내기\` |
| Lv.1 로그인 회원 | **나의 추천 링크**, 진행률 \`0/1명\` | \`추천 링크 복사\` |
| Lv.2 로그인 회원 | 레벨2 활성화 | \`레벨2 이용하기\` |
| Lv.2 비로그인, 기존 저장 세션 없음 | 아이디+비밀번호 로그인 | \`로그인\` |

서버가 검증한 응답 상태에 따라서만 레벨 UI 변경. 클라이언트 level/localStorage/UUID 값을 믿지 말 것.

**추천 성공 문구**
- 제목: \`레벨2가 열렸습니다!\`
- 본문: \`동료 선생님의 설문 참여로 레벨2가 활성화되었습니다.\`
- 버튼: \`레벨2 이용하기\`
(기존 정책의 “다른 기기에서도 이용하고 싶으신가요?” 가입 유도는 불필요하므로 제거.)

## 2. 계정과 레벨의 데이터 구조

- Supabase Auth: 이메일 확인 + 이메일/비밀번호 실제 인증. UX는 아이디+비밀번호 로그인; 개인 username→auth user/email 내부 매핑은 서버에서만 수행. 인증 사용자 ID는 Auth 검증을 통해 확인, 클라이언트가 제출한 user_id로 권한 부여 금지.
- 비공개 account_profiles: \`auth_user_id\` PK(FK auth.users), \`username_canonical\` UNIQUE, \`created_at\`, \`disabled\`.
- 비공개 account_level_profiles: \`auth_user_id\` PK, \`access_level\`(0/1/2), \`level1_verified_at\`, \`level2_upgraded_at\`, \`disabled\`.
- 비공개 account_referrals: \`auth_user_id\` PK, \`referral_token_sha256\` UNIQUE, \`valid_referrals\`(0/1), \`created_at\`, \`revoked_at\`. 추천 링크의 원문 토큰 보관/재발급 정책은 안전한 임의 토큰 및 안전한 복구·회전 방식으로 설계(예: 버전 키 기반 HMAC)한다.
- 비공개 account_referral_events: \`event_sha256\` PK, \`referral_token_sha256\`, \`respondent_sha256\`, \`decision\`, \`created_at\`, \`referrer_auth_user_id\` FK. 같은 제출 이벤트 멱등 처리, 동일 응답자 브라우저 UUID 중복 적립 방지, 자기 추천 방어(가능한 범위 내).
- Lv.1을 비회원으로 인증한 기존 세션은 그대로 사용. Auth 계정 연결 단계에서 **현재 유효한 Lv.1 서버 세션을 요청자 Auth 사용자에게 안전하게 결속**. 계정별 level은 서버가 관리하고 다른 기기 로그인 시 재조회.
- 계정이 완전히 검증된 상태이면서 level 1 이상인 경우에만 추천 토큰 반환. 회원가입만으로 추천 링크 발급 불가.
- **기존** \`challenge_referral_profiles\`에는 \`visitor_id\`, \`identity_code_sha256\` 필수 제약이 있으므로 새로운 account 레코드를 여기에 억지로 넣지 말 것. 신규 account 기반 원장으로 독립 구현. \`challenge_identity_codes\`, 개인번호 3종, 기존 참가자 데이터는 지우지 않는다.
- 역할 분리: 가입했다고 곧바로 Lv1이 아님; 공통번호 입력 성공 시 Lv1; 유효 추천 1회 시 Lv2.
- 기존 Lv.1 공통번호는 **공유된 자격**이므로 실제 교사 신원 증명이 아니다. 다계정·부정 승급 가능성, 계정/인증 시도 제한 및 CAPTCHA·모니터링 검토.
- 구글폼 prefill 응답자 UUID는 변경 가능한 값이다. 실제 사람 식별이 아니라 약한 중복 신호임을 명시하고, 추적·반복·자기 추천 남용을 정책상 허용하지 말되 완전 차단을 주장하지 않는다.

## 3. 1차 작업과 연동

### 유지
- 기존 Lv.1 학교 검색·비교·공통번호 검증 및 서버 세션
- 기존 공식 Google Form URL과 전체 설문 답변/집계 흐름
- 기존 두 선택 문항: \`BG26 추천 확인값 (자동 입력)\`, \`BG26 기기 확인값 (자동 입력)\`
- \`scripts/beagu-2026-noon-sync.gs\`, \`scripts/beagu-2026-referral-addon.gs\`(Referral.gs), \`installBeagu2026ReferralBridge\` 설치 과정
- \`js/referral-form-config.js\`의 실제 entry ID 설정과 \`survey.html\` 사전입력
- \`beagu-referral-v1\`의 Apps Script ingest 포맷: \`{action:'ingest',eventKey,referralToken,respondentUuid}\`. 이 전달 포맷 그대로 둔 채, 서버의 적립 대상과 RPC는 **새 계정 원장**으로 교체.
- \`challenge_identity_codes\`의 과거 발급 내역은 보존(인증에는 사용하지 않음).

### 변경/제거(2차 구현 시)
- **삭제** \`beagu-referral-v1\` \`action=login\` 고유번호 직접 로그인, \`action=enroll\` visitor+identityCode 추천 링크 발급.
- **미사용/정리** \`public.beagu_referral_auth(p_identity_hash)\`, \`beagu_referral_enroll\`, 그리고 이들 RPC를 호출하는 신규 경로; 기존 설치 SQL을 무리하게 돌이켜 DB 객체를 삭제하지 않음. 권한 없는 레거시 객체는 차후 별도 정리.
- **개편** \`search-lv2.html\`, \`js/level-search.js\`, \`js/beagu-level-state-v1.js\` 로그인 경로를 Supabase Auth JWT+현재 서버 레벨 조회로 교체.
- **개편** 홈/상단 공통 내비게이션과 레벨 설명/레벨업 모달: Lv0부터 로그인/회원가입 + 0→1 공통번호 인증 + 1→2 추천 링크. 챌린지 화면은 레벨업 동선에서 제거.
- **신규** \`beagu-account-v1\` Edge/API(또는 적정 분리), account/level/referral DB 마이그레이션, 로그인/회원가입/이메일확인/비밀번호재설정 UI 및 tests.
- **고유번호 발급 API 취약점**: 1차 운영 \`beagu-challenge-identity\`의 타인 UUID 조회 가능성은 계정 인증 경로에서 제거하더라도 별도로 차단해야 한다. API 무단 변경/배포 대신 별도 패치와 회귀테스트 후 승인 받기.
- **고유번호 및 챌린지 의존 테스트**: 1차 테스트 중 code login 성공 및 challenge referral panel 기대값은 2차 테스트에서 교체. 추천 ingest 자체 테스트는 유지.

## 4. 안전 조건

1. 프론트에 Supabase service_role 노출 금지. Auth JWT 및 개인정보 접근은 서버 검증, 비공개 DB + RLS/최소 권한.
2. 아이디 중복, 이메일 확인, 계정 재등록, 비밀번호 재설정, 레이트 리밋, 세션 철회/만료, 탈퇴/정지 계정 거부 구현.
3. 공통번호로 임의 계정의 Lv1을 올리는 요청을 수락하지 않음: 요청자의 Auth JWT와 **동일 요청의 서버 Lv1 검증 결과**를 매칭(기존 공유 세션 그대로 타 사용자에 무제한 귀속하지 않도록 바인딩 정책 결정).
4. 추천 링크는 짧은 추측 가능한 식별자 금지. 탈취·재발급 시 해시 회전과 구토큰 적립 차단 구현.
5. 서버에서 정상 추천 1회가 확인되면 account의 access_level=2를 **원자적으로** 설정하고, 동일 제출 재실행·동시 제출 중복 적립 방지.
6. 폼의 추천 prefill 문항이 사용자에게 보이고 수정 가능하다는 한계를 인정. Google Forms 제출 1건=진짜 별개의 교사 1명이라는 강한 보장은 불가능.
7. 계정 생성은 Lv0부터 허용하지만, 일반 Lv0·Lv1은 회원가입 없이 계속 사용할 수 있다.
8. 작업 완료 전 \`public_enabled\`, \`ingest_enabled\`, \`login_enabled\`은 모두 **false**로 유지. 신 account 기능별 플래그도 OFF.
9. GitHub PR #49는 Draft로 두고 운영 Edge, main, Forms, Apps Script 및 Supabase 실제 스키마는 이번 설계 수립 단계에서 변경 금지.

## 5. 2차 개발 구현·검증 순서

P0. Google Forms 원본 문항 2개 / 실제 entry ID / Apps Script 설치 상태 확인. 기존 집계 변경 없음.
P1. 계정 DB 모델 및 플래그 **새 마이그레이션 파일만 작성**하고 개발 환경에 테스트. 모든 사용자 접근 차단/RLS 점검.
P2. Lv0 회원가입, 이메일 확인, 아이디/비밀번호 로그인, 비밀번호 복구 구현. 미가입 사용자 Lv0 기능 그대로.
P3. Lv0 → Lv1 공통번호 인증을 서버 Auth 사용자 ID에 귀속. 로그인되지 않은 기존 Lv1 간편 방식 보존.
P4. Lv1 → Lv2 로그인 계정에 단일 개인 추천 링크 발급. 토큰 관리/회수/동일 사용자 재발급 보안.
P5. 기존 Forms 트리거/Apps Script ingest의 payload는 유지하면서 새 \`account_referral_events\`에 트랜잭션으로 적립하고 \`account_level_profiles.access_level=2\` 갱신. 폼 답변은 전송 금지.
P6. ‘레벨업하기’ 전체 UI 및 헤더 레벨 상태 연동, Lv2 계정 접근 검증, 기존 고유번호 로그인 관련 경로/테스트 정리.
