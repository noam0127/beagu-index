# 회원관리 v2.0 — 8단계 대량회원/보안 회귀 점검

## 확인된 실제 결함 및 수정
- 7단계 API에 `const status` / `const sort` 중복 선언: TypeScript 구문 오류 위험. PR #215 브랜치에서 중복 제거.
- 7단계 API가 `page <= 200`을 강제: 20명/페이지일 때 4,000명 이후 페이지 접근 불가. 최대 1,000,000페이지로 수정. 운영 배포 전 실제 페이지 이동 검증 필요.
- 회귀 정적 검사 `tests/admin-member-pagination-regression.cjs` 추가.

## 보안 점검
- `beagu_admin_member_directory_v2`는 `SECURITY DEFINER`이므로 `PUBLIC`, `anon`, `authenticated`에 EXECUTE를 부여하면 안 됨. SQL에서 REVOKE 및 service_role만 GRANT하는 것 확인.
- Edge Function의 관리자 JWT 검증, AAL2 및 활성 MFA 세션 검증이 목록 호출 이전에 유지되는지 확인.
- 회원 이메일과 UUID가 관리자 응답에 포함됨: 기존 브라우저 마스킹 PR #206만으로는 서버 개인정보 최소화가 달성되지 않음. 별도 서버 응답 정책 필요.
- 실제 DB 적용 이후 권한 검증(anon/authenticated RPC 호출 거절, service_role 허용)을 필수로 수행.

## 성능 및 정합성 한계
- 전체 사용자 수·관리자 수·미인증 수·정지 수 집계를 요청마다 각각 계산. 회원 수가 커지면 DB 부하가 증가할 수 있음. 캐시/별도 집계 및 EXPLAIN ANALYZE 필요.
- `strpos(lower(email),lower(search))` 부분검색은 일반 B-tree 인덱스만으로 효율화하기 어려움. 실제 규모에서 검색 성능 검증 필요.
- OFFSET 페이지네이션은 뒤쪽 페이지에서 느려질 수 있으며, 동시에 가입/삭제가 발생하면 페이지 간 항목 중복·누락이 생길 수 있음. 대규모 목록은 커서 페이지네이션 검토.
- 현 API는 전체 회원 목록을 반환하지 않고 요청 페이지 20명만 반환하나 전체 통계 계산은 수행함.
- 현재 실사용 4,000+/10,000+ 건 성능 측정은 하지 않았으므로 성능 목표 달성으로 표시하면 안 됨.

## 운영 적용 전 테스트 게이트
1. TypeScript/Deno 타입검사 및 Node 정적 검사 전부 실행
2. 별도 테스트 DB에 4,001·10,001명 모의 계정으로 201·501페이지 및 검색/정렬 검증
3. 인증 없음/AAL1/MFA 세션 만료/관리자 권한 없음/관리자 유효 세션 접근 테스트
4. 서비스 역할 외 RPC 실행 권한 거부 확인
5. SQL 실행 계획, 응답 시간, 과부하/타임아웃 측정
6. 기존 회원 상세·정지·복구·감사 로그 기능 회귀 테스트
7. DB RPC를 먼저 준비하고 서버 코드를 후속 배포해야 하며 이 채팅에서 배포하지 않음
