# v1.10.1 통합 관제탑 — 독립 개발

## 7단계
1. 웹 단독 적용 차단: GitHub 변경 파일(삭제/이름 변경 포함)에서 Supabase 및 배포 제어 코드 검출, 관리자 상태 및 큐 승인/작업자 claim에서 fail closed. 등록은 배포가 아니다.
2. 승인된 버전의 명시적 변경 명세와 신뢰된 실행기 allowlist, immutable SHA/파일 digest 검증. 후보가 임의 셸/SQL 실행 권한을 획득하면 안 된다.
3. 비공개 백업/복원 검증과 기존 데이터 fingerprint, 잠금 및 쓰기 차단 계획. 비밀/백업 공개 금지.
4. 백업→DB→Edge→검증→Pages→운영 확인 순서와 단계별 durable 상태/원자적 lease. 관리자 MFA로 하나의 불변 계획 승인. DB/Edge 변경이 남으면 Pages 차단.
5. 중단/재시도/전진 복구: 실패한 단계 이후 진행 금지; 부분 서버 적용 후 자동 재실행·웹 단독 롤백 금지; 신규 데이터 보존 및 별도 복구 승인.
6. 관리자 UI에서 통합 계획/영향/확인/진행/오류 표시. 비밀은 브라우저에 노출하지 않는다.
7. 격리 실환경 회귀, 오류 주입, 데이터 보존, 관리자 인증, 기존 단독 웹 배포, stale/duplicate job 테스트. 실제 적용은 별도 승인.
## 최초 설치 제약
이 변경 자체도 백엔드 변경이므로 기존 Pages 버튼만으로 설치할 수 없다. 승인된 일회성 부트스트랩으로 신뢰된 제어 서버와 작업자를 먼저 설치하고 확인해야 한다. 자동 통합 실행은 아직 구현되지 않았다.
계정 후보와 다른 개발 브랜치는 병합하지 않는다. 완료된 관제탑 운영 SHA 기준으로 계정 후보를 새로 통합하고 전체 CI 재검증.

- 1단계 기준 SHA `9f455312afb7b5f86bdebf1d00785f3bffaf5cda`: CI 4/4 성공 (45360315308, 45360315254, 45360315251, 45360315287).
- 2단계 읽기 전용 API: 관리자 MFA 인증 후 `inspect_integrated_plan`. 등록 후보 SHA 및 예상 운영 SHA 필수, 정확한 후보 CI 및 버전/설명 일치 확인, 응답 직전 상태 재확인. 변경 목록은 GitHub compare에서 읽으며 300개 이상/잘못된 경로/중복/누락된 Git blob SHA를 거부한다.
- 명세 schema 1 / integrated-review-v1: repo, base/candidate SHA, version/summary, 변경 유형, Git blob SHA 및 base/candidate 위치, rename 이전 경로, 고정 분류, 공유 의존성 및 수동 검토 요구, 변경된 Edge 함수 이름. 정렬된 JSON의 SHA-256을 서버에서 산출한다. 이전 digest와 다르면 409. 후보나 브라우저가 제시하는 실행 명령/승인 여부는 무시한다. 서버가 정한 검토 종류 외의 명령은 없으며 execution_enabled=false. 등록·승인·작업 생성·실행은 하지 않는다.
- 이 명세는 검토용 인벤토리이지 실행 승인서가 아니다. 다음 단계에서 실제 Git tree/파일 바이트 검증, 검토된 DB 적용 순서, 별도 승인 및 신뢰된 고정 실행기 작업 allowlist, 공유 모듈 배포 대상 검증, 체크포인트와 durable 승인 저장이 필요하다. GitHub compare의 blob SHA만으로 파일 내용이나 실제 DB 적용 안전성을 인증하지 않는다. 운영 설치 금지.

## 2단계 실제 파일 및 신뢰된 작업 검증 후보
- 이전 명세 API CI 4/4 성공: e5a3a425b2301b8e6cced6063a199e140ab0a926.
- trusted controller의 integrated_verify.py는 실제 Git commit/ancestor, 전체 no-renames delta와 inventory의 완전 일치, Git tree regular-file mode, Git blob SHA-1 및 실제 bytes SHA-256, 이전 파일 bytes, metadata 및 분류를 독립 검증한다. 후보를 checkout하거나 실행하지 않는다. 미지원 변경/링크/누락/초과 크기는 차단한다.
- 고정 작업 목록 backup/apply_sql/apply_scheduler/deploy_edge/verify_backend/publish_pages/verify_live. 신뢰된 controller에 위치한 registry의 정확한 base/candidate/plan SHA 및 file SHA-256 pin과 일치해야 한다. 순서, 파일 중복/누락, Edge 범위, 수동 검토 대상, 미지원 명령을 거부한다. 초기 registry는 비어 있으므로 실제 운영 작업 허용 없음. 계정 후보 재통합 및 리뷰 후 정확한 recipe를 별도 승인한다.
- 아직 실행 handler, 운영 연결, 승인 저장 또는 자동 게시 경로에 연동하지 않는다. 검증 성공도 execution_enabled=false. 실제 실행 전에 전체 Edge 패키지(변경되지 않은 의존성 포함) 검증과 신뢰된 배포 runner 연결이 별도 필요하다. CI는 임시 로컬 Git 저장소를 사용한다.

## 3단계 백업·복원 검증 후보
- 2단계 정확한 후보 SHA `275e136e8f17167be4156b6e052bf756e8392bf1` 전체 CI 4/4 성공 (45361249306, 45361249475, 45361249319, 45361249366).
- integrated_backup.py: 새로 생성하는 네트워크 격리 Docker PostgreSQL 16 fixture 전용. 운영 연결 문자열·기존 컨테이너·원격 Docker 입력 불가. 읽기 전용 exported snapshot, pg_dump custom, 동일 snapshot의 데이터 fingerprint, sequence 및 schema/ACL fingerprint, 종료 직후 source 재확인. 새 빈 DB에 pg_restore single transaction으로 복원. 기존 DB 덮어쓰기 금지.
- 체크포인트는 mode 0700 디렉터리와 0600 파일, exclusive/no-follow, fsync, dump SHA-256, 별도 보존한 최신 manifest digest, plan/base/candidate pin을 요구한다. CI에 private dump를 artifact로 올리지 않는다. 복원 전후 source/restore fingerprint 대조, 오래된 파일/권한/변조/스테일 source 차단. CI fixture는 가상의 참여번호·추천·게시물과 RLS/권한/시퀀스를 사용한다.
- 이 단계는 실제 격리 DB 복구 리허설 구현이며 운영용 백업 완료를 뜻하지 않는다. 운영용은 전체 schema/extension/Auth/Storage/Edge 및 외부 의존성 인벤토리, 별도 안전한 암호화 백업 저장소/보존/키 정책, writer freeze와 release lock, 독립적인 durable latest manifest, 승인된 접근권한·복원 계획이 필요하다. 시퀀스는 MVCC가 아니므로 실제 writer freeze 없이 운영 백업 허용 금지. 운영 데이터나 백업을 읽거나 변경하지 않는다.

## 3단계 암호화 저장 후보
- 기존 실제 격리 PostgreSQL 백업·복원 CI 4/4 성공: `17c5690e8d0b0cbf35ce15d2c0cb47fddc90486e` (45361696047,45361696136,45361695915,45361696072).
- integrated_vault.py: 표준 cryptography AES-256-GCM, 무작위 96-bit nonce 및 256-bit 외부 주입 키. DB dump와 데이터 fingerprint/manifest를 메모리에서 암호화하여 단일 객체 저장. plan/base/candidate/checkpoint/key ID를 AAD와 독립 pin에 결합. 독립 pin, 키, AEAD 인증, dump hash가 모두 일치해야 복호화. 객체 0600, 디렉터리 0700, fd 기준 no-follow, atomic no-replace link 및 fsync. 백업 파일 덮어쓰기 금지. CI에 키/평문/객체 업로드 금지.
- 실제 DB fixture의 암호화 백업에서 pg_restore 경로 연결. 잘못된 키, 변조된 암호문, 다른 release pin, 권한, 링크, 중복 객체, 키 교체 및 오래된 체크포인트 거부 검사. 운영 연결/설치 금지.
- 운영용 저장소 adapter의 로컬 보안 구현 후보일 뿐 운영 저장소가 만들어졌거나 백업 완료된 것이 아니다. 운영에는 신뢰된 전용 runner의 private 암호화 볼륨 또는 승인된 private object store, 별도 KMS/key provider 및 독립 durable latest pin, 암호화 키 백업/rotation, 접근 로그·보존 정책과 별도 삭제 승인, 데이터 크기 및 스트리밍/복구 검증, Auth/Storage/Edge/확장 포함 전수 백업 범위, writer freeze가 필요하다. 현재 scope는 isolated_fixture_only로 고정하며 실행 권한은 false. CI는 OS 유지관리 cryptography 라이브러리 사용, 운영 runner의 버전 및 공급망은 부트스트랩 때 별도 고정/검증. Python 메모리 zeroization은 보장하지 않으므로 전용 프로세스 및 코어덤프/스왑 제한 필요.
