# 배구지수 v1.1.0 — 14단계 휴대폰번호 저장·동의 이력·철회·RLS 보안 설계 및 검증

> **운영 적용 금지(현재):** 4단계 운영 DB 암호화 백업·분리 복원 미검증, 5단계 Auth Redirect URL 원격 설정 미검증. 이 문서는 GitHub 개발 브랜치의 **적용 전 설계·검증 결과**이며 운영 DB의 실제 변경 기록이 아닙니다.

## 운영 Supabase 읽기 전용 조사에서 확인한 사실 (2026-11-21)

대상 운영 프로젝트: `snvzwrexuqavnfvzgxqj`.

- 기존 `beagu_private.member_sms_subscriptions_v1` 테이블이 이미 존재함. `user_id`, `phone_e164`, `sms_consent`, `consent_version`, `consent_source`, `consented_at`, `withdrawn_at`, `phone_verified_at`, `updated_at` 필드 확인.
- 테이블 RLS 활성화, `relacl`에 `postgres`만 존재. **그러나 RLS만으로 동의의 진정성까지 보장하지는 않음.**
- **보안 결함:** `auth.users`에 `capture_member_sms_consent_v1` 트리거 활성. 그 함수는 계정의 사용자가 수정할 수 있는 `raw_user_meta_data`의 `beagu_sms_opt_in`과 `beagu_sms_phone`에 따라 비공개 테이블의 번호/수신 동의를 기록. 이는 신뢰 가능한 별도 동의 원장으로 간주할 수 없음.
- `public.beagu_admin_member_sms_status_v1(uuid[])` RPC 존재(일반 브라우저 역할 EXECUTE 없음). 새 프로덕션 운영 전에는 이 기존 조회 함수도 v2 동의 검증 상태와 일치하는지 별도 점검 필요.
- 실제 사용자 번호, 이메일, Auth 토큰 또는 동의 행 내용은 **조회·출력하지 않음**. 모든 SQL 점검은 시스템 카탈로그 메타데이터에만 한정.

공식 참고: [Supabase User Metadata](https://supabase.com/docs/guides/auth/users), [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 개발 브랜치에서 구현한 변경 사항

### 1. 기존 테이블을 활용한 비공개 DB 마이그레이션

파일: `supabase/migrations/20261121230000_beagu_member_sms_consent_secure_v2.sql`.

- 기존 Auth `raw_user_meta_data` 기반 트리거/함수 제거.
- 기존 `beagu_private.member_sms_subscriptions_v1` 재사용. `phone_collection_consent` 및 `consent_confirmed_at` 추가.
- **기존 사용자 메타데이터 기반 동의 번호는 신뢰 가능한 승인을 받은 기록이 아니므로, 적용 시 이 테이블의 해당 개인정보를 제거하고 SMS 동의 상태를 비활성화함.** 이 일괄 삭제는 운영 승인·백업 후에만 수행해야 함.
- `beagu_private.member_sms_consent_events_v2`에 수신 신청, 동의 철회, 기존 값 정리 이벤트를 기록. 감사 이력에는 **전화번호·이메일·토큰·IP·원본 요청 본문을 저장하지 않음**. 계정 삭제 시 사용자 참조 및 이력 함께 삭제.
- 두 테이블 RLS 활성화, `anon`·`authenticated`·`PUBLIC`에 직접 테이블 CRUD 권한 미부여.
- `public.beagu_member_sms_grant_v2`, `public.beagu_member_sms_withdraw_v2`, `public.beagu_member_sms_status_v2`는 **service_role EXECUTE 전용**. `SECURITY DEFINER` + 빈 `search_path`, 명시적 스키마 참조; `anon`·`authenticated`의 EXECUTE 권한 즉시 REVOKE.
- 가입 이메일 확인이 완료된 사용자의 별도 수집·수신 동의 두 항목이 모두 참인 경우에만 번호를 기록. 번호는 `+82...` 형식으로 저장.
- 재동의 시 기존 휴대폰 인증을 무효화(`phone_verified_at=NULL`). **SMS 발송 권한은 번호 인증이 완료되기 전까지 허용되지 않음.**
- 철회 시 동의 상태와 번호, 번호 검증 정보를 즉시 비활성화·삭제하고 별도 감사 이벤트를 남김.

### 2. 인증 사용자 전용 서버 API

파일: `supabase/functions/beagu-member-sms-api-v2/index.ts`.

- POST `action=status|opt_in|withdraw`, 사용자 JWT를 `auth.getUser(jwt)`에서 서버 검증하고 이메일 확인·비익명 계정만 허용.
- 전화번호나 동의 여부를 회원가입 메타데이터에서 복사하거나 임의 클라이언트 `user_id`를 받지 않음. 실제 데이터베이스 사용자 ID는 **서버가 확인한 `user.id`**에서 얻어 RPC에 전달.
- 두 개의 명시적 동의와 `010` 11자리 형식을 확인하고, 서비스 역할의 제한된 RPC로만 비공개 테이블 조작.
- 철회 완료 시 Auth의 과거 `user_metadata`에 남았을 수 있는 SMS 연락처 키 삭제도 관리자 Auth API로 시도. **메타데이터 삭제 실패 시 완전 삭제 성공으로 응답하지 않음.**
- 단일 가입 상태조회에는 동의 여부 및 번호 인증 여부만 응답하고 원본 번호·이메일을 반환하지 않음.
- CORS 허용 출처 제한, POST/OPTIONS 제한, 작은 JSON 본문 한도, `Cache-Control:no-store`, 서버 로그에 전화번호 기록 없음.
- 실제 발송 시스템이나 인증되지 않은 번호에 대한 문자 전송 기능은 추가하지 않음.

### 3. 회원가입 시 개인정보 미전송 및 로그인 후 별도 설정

파일: `js/beagu-sms-account-settings-v2.js`, `js/challenge-member-auth-v1.js`, `js/postit-account-v1.js`, `js/beagu-account-mode-v1.js`, `challenge.html`, `postit.html`.

- **13단계의 초기 ‘가입할 때 전화번호를 Auth metadata에 전송’ 방식은 14단계 보안 검토에 따라 폐기.** 회원가입 `signUp` 호출에는 전화번호나 동의 플래그를 보내지 않음.
- 이메일 인증 후 로그인한 사용자의 별도 문자 수신 설정에서만 수집/수신 동의 체크박스 및 번호 입력 활성화. 각각 **기본 미체크**.
- 두 동의와 정상 번호가 있는 경우에만 인증된 서버 API로 수신 신청. 계정 로그인·포스트잇 작성·Lv2/Lv3 권한과 수신 동의 상태를 혼합하지 않음.
- 서버 수신 상태를 조회하여 철회 버튼 노출. 철회 실패 시 삭제 성공 문구를 표시하지 않음.
- 로그아웃/회원가입 모드 전환 시 입력된 전화번호와 선택값 초기화. 로컬스토리지/세션스토리지에 번호 저장 안 함.

## 출시 전 필수 조건 (차단 유지)

1. **실제 운영 DB의 암호화 백업과 격리 환경 복구를 검증**하고 권한이 있는 관리자가 DB 변경을 승인한다. 백업 없이 운영 테이블/트리거에 마이그레이션을 적용하지 않는다.
2. 우선 시험 DB에 마이그레이션, 서버 Edge Function, 프런트엔드를 순서대로 적용한다. 시험 웹에서 실제 가입·메일 확인·로그인·번호 신청·철회·회원탈퇴 후 삭제를 **합성 계정**으로 검증한다.
3. **중요 잔여 개인정보 정리:** 이미 존재하는 일부 Auth 사용자의 `raw_user_meta_data` 안에 과거 `beagu_sms_phone`이 남아 있을 가능성이 있다. 마이그레이션은 비공개 구독 테이블을 정리하지만 **모든 기존 Auth 메타데이터의 연락처를 자동 제거하지는 않는다**. 실제 저장 여부를 사용자 정보를 외부에 출력하지 않는 방식으로 점검하고, 검증된 Auth Admin API 기반 일괄 제거를 별도 승인·실행해야 한다.
4. 기존 `beagu_admin_member_sms_status_v1`을 비롯하여 구형 동의 기록을 보는 관리자 화면/발송 시스템에 대한 추적 감사를 진행한다. 서버 인증·실시간 번호 검증·동의 이력·수신 철회 반영·광고성 문자 발송 요건을 모두 검증하기 전에는 **어떤 문자도 발송하지 않는다**.
5. 운영 및 시험의 `Supabase Authentication → URL Configuration` 허용목록(5단계)과 6~11단계 계정 E2E 검증을 완료한다.
6. 보유 기간/마케팅 동의 내용/연락처 파기 의무/법적 보존 사유는 실제 서비스 개인정보처리방침 및 국내 법령과 일치하도록 검토한 후 운영에 반영한다.

**본 단계는 개발·격리 검증 단계이며 실서비스 SMS 저장·발송 기능의 운영 완료를 의미하지 않는다.**
