## 참여코드 Lv.1·Lv.2 설문증명 분리 — 실제 구조적 차단사항

2026-11-22 운영 함수·현재 배포된 시험 API **정의/코드만 읽기 전용으로 비교**한 결과, 확정된 참여코드 권한 규칙과 실제 구현 사이에 중요한 차이가 있음.

**확정할 권한 규칙:** 2026 설문 완료가 독립적으로 검증되었을 때 발급 코드에 Lv.1을 부여하고, 그 코드의 유효한 추천 응답 1건이 검증되면 같은 코드가 Lv.2로 상승한다. 단순히 코드를 보유·발급받은 사실, 챌린지 참가번호를 부여받은 사실은 설문 완료 증명이 아니다.

- 운영 `beagu_issue_challenge_identity(p_visitor)`는 `beagu_private.participants`에 참가번호를 만들고 `challenge_identity_codes`에 고유번호를 발급한다. 코드 자체가 실제 설문 제출 완료를 검증하는 구조는 아님. `participants` 테이블도 `campaign, visitor_id, participant_no, joined_at`으로, 설문 완료 확인 컬럼이 없음.
- 배포된 시험 `beagu-level-api`의 login 분기는 기존 `beagu_level_codes`를 먼저 검사하고, 그것이 없으면 `beagu_earned_challenge_visitor(p_code)`만 호출한다. 이 RPC는 유효 추천을 확인한 Lv.2 방문자만 반환하므로 **설문 참여는 했지만 아직 추천이 없는 사람의 고유번호가 Lv.1로 승인되지 않는다**. 이것이 기존 요구사항에 비해 부족한 현재 동작.
- `beagu_earned_challenge_visitor`는 `valid_referrals>=1`, `access_level>=2`, `upgraded_at IS NOT NULL`, `disabled=false`, 코드 해시 일치를 검증한다. **이 Lv.2 권한 검증을 약화하면 안 된다**.
- `beagu_referral_enroll`의 발급/등록 경로는 설정 `public_enabled`에 의해 제한되며, 기존 함수는 실제 설문 제출 사실을 원천적으로 대조하지 않는다. 향후 Lv.1 추가 RPC는 **별도로 확인된 2026 설문 참여 증빙을 원천으로 연결하는 서버 전용 증명**이 필수다. 설문 참가자 신원을 추정하거나 실설문·사용자 행을 시험 DB로 반입하지 않는다.
