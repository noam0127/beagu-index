# 배구지수 v1.1.0 — 17단계: 2026 인증코드 Lv1·Lv2 서버 판정

**상태:** 개발 브랜치 구현·독립 PostgreSQL/CI 검증 전용. **운영/시험 Supabase의 DB·Edge Functions 및 공개 웹에 아직 적용하지 않음.**

## 17단계의 정확한 권한 규칙

| 2026 고유번호/추천 상태 | 서버가 인정할 권한 |
|---|---|
| 발급만 됐고 본인 2026 설문 응답 증명이 없음 | **Lv0(인증 거절)** |
| 2026 본인 응답이 Google Forms 원본으로 검증됨, 추천 0건 또는 심사 보류 | **Lv1**. 프로필이 'Lv2 참여코드(비활성)'이라도 **고유번호 그대로 Lv1** |
| 본인 2026 응답 검증 + 중복/품질검사 통과·공인된 추천 1건 이상 + 활성 프로필 | **Lv2**. 동일 고유번호 사용 |
| 보류/반려/취소/비활성 추천, 본인 응답은 유효 | **Lv1로 강등** |
| 본인 2026 응답이 최종 취소·반려됨 | **Lv0(2026 코드 인증 거절)** |
| 별도 2023–2025 기존 참여코드 | **기존 인증 정책 보존** |

**Lv3는 17단계 작업 대상이 아니다.** 고유번호 소지 자체, 챌린지 순번, 추천 링크 방문, Google Form 연결 페이지 접속은 설문 *제출 완료 증거가 아니다*.

### 운영 구조 점검 결과

운영 DB는 **개인정보/개별 코드/응답 행을 조회하지 않는 시스템 카탈로그 읽기 전용 조회**로 점검했다.

- `beagu_private.challenge_identity_codes`: 방문자 UUID·기존 고유번호·순번·발급시각. 설문 완료 여부 필드 **없음**.
- `beagu_private.challenge_referral_profiles`: 유효 추천 수, Lv2 상태, 비활성 여부. 이는 **다른 사람의 추천 인정 여부**이며 고유번호 소유자의 **본인 설문 응답 증거는 아님**.
- `beagu_private.challenge_referral_events` 및 `challenge_referral_quality_reviews`: `credited` 여부, `AUTO_PASS`/수동 승인과 원본 품질 확인. 승인 중/반려 중/중복 의심 사건을 유효 추천으로 인정할 수 없음.
- `public.beagu_level_sessions`: 만료시각·권한 등급·2026 방문자 연결 식별자. 현재에는 2026 방문자 세션이 Lv2일 때만 추천 수를 재검증하고, Lv1 비활성 개인코드를 승인하는 분기 없음.
- 기존 `beagu_earned_challenge_visitor`는 추천 1건을 확인하지만 자체로 **본인 2026 설문 완료를 확인하지 않음**.
- `public.survey_submissions`은 현재 스키마상 연도/학교/제출시각을 포함하지만 방문자 UUID 및 고유번호와 증명 가능한 1:1 연결이 없음. 이를 임의 추측하여 결합하지 않음.
- `scripts/beagu-2026-referral-integration.gs`의 2026 공식 Google Forms 제출 트리거는 추천용 `BR1` 증거 문항을 사용한다. **전체 응답자에게 고유번호 소유자 방문자 UUID를 확인해 주는 본인 설문 연결은 아직 독립적으로 검증되지 않음.**

## 구현 파일

### 1. 검증된 원본 설문 응답 비공개 원장

`supabase/migrations/20261121235500_beagu_2026_verified_code_levels_v1.sql`:

- `beagu_private.challenge_2026_verified_responses_v1`: 이미 발급된 2026 고유번호의 방문자 UUID, Google Form 응답 고유 ID를 **서버 전용 HMAC으로 변환한 값**(중복 방지), 검증 일시, `approved/revoked/review_required` 상태만 저장. 응답 원문·전화번호·이메일·개별 질문 답변은 미수집.
- `beagu_private.challenge_2026_verification_events_v1`: 검증/철회/품질 보류 이력. RLS·`anon`/`authenticated` 접근 금지.
- `beagu_2026_record_verified_response_v1`: `service_role`만 호출할 수 있는 원본 응답 검증 기록 함수. 기존 발급코드 재발급·변경 없음; 동일 Google Form 출처증거를 두 고유번호에 중복 연결할 수 없도록 유일 제약.
- `beagu_2026_verified_visitor_level_v1`: 본인 2026 응답의 `approved` 상태가 없으면 Lv0, 있으면 최소 Lv1. Lv2는 `challenge_referral_profiles`의 활성 1건 이상뿐 아니라 **실제 `credited` 사건과 `AUTO_PASS + form_quality_attested` 또는 `MANUALLY_APPROVED` 품질 증거**까지 필요.
- `beagu_2026_verified_code_level_v1`: 기존 10자 Base32, 12자 그룹형, 26자 구형 고유번호의 **값 그대로** 코드에 연결. 이미 발급된 코드지만 증명이 없는 것은 `known:true, level:0`으로 구분해 구형 Lv1 코드를 우회 조회하지 못하게 함.
- 기존 서비스가 이용 중인 `beagu_has_earned_challenge_visitor` 및 `beagu_earned_challenge_visitor`의 보안 검사를 이 새 검증 규칙으로 교체하여 포스트잇 권한 우회 방지.

### 2. 실제 웹 인증 서버와 추천 링크 갱신

- `supabase/functions/beagu-level-api/index.ts`: 모든 2026 고유번호는 `beagu_2026_verified_code_level_v1`를 먼저 조회. 검증이 없으면 로그인 불가, 있으면 Lv1/Lv2에 맞는 6시간 세션 생성. 2026 권한 세션은 **매 보호된 API 호출마다** `beagu_2026_verified_visitor_level_v1`를 다시 확인; 추천이 사후 반려되면 Lv2→Lv1, 본인 응답이 철회되면 세션 거부. 별도 2023–2025 `beagu_level_codes` 조회는 그대로 보존.
- `supabase/functions/beagu-referral-link-v1/index.ts`: 추천 응답 1건의 카운트만으로 권한을 올리지 않음. 새 서버 검증 함수가 내린 실제 등급을 통해서만 기존 세션을 고유번호 방문자에 연결하고 승급. `ownResponseVerified` 서버 값을 화면으로 전달.
- `js/challenge-referral-v1.js`: 고유번호 발급 직후 `나의 고유번호`와 `인증 대기`; 본인 응답 검증 뒤 **Lv1 참여코드**; 본인 응답+유효 추천 뒤 **Lv2 참여코드**. 세 상황 모두 원본 고유번호 문자열 불변. 단순 `payload.level=2` 같은 클라이언트 값만으로 승급 화면 미표시.
- 통합 참여코드 입력 모달·학교검색·학교비교 및 포스트잇은 **이 서버 세션 등급을 그대로 따른다**. Lv3 별도 계정 검증은 변경하지 않는다.

### 3. 2026 Google Forms 전용 원본 증명 서버 초안

`supabase/functions/beagu-2026-participation-ingest-v1/index.ts`:

- 서버-서버 POST만 허용, 브라우저 Origin 차단. 별도 보관한 `BEAGU_2026_PARTICIPATION_INGEST_SECRET`(32자 이상) 검증과 `BEAGU_2026_PARTICIPATION_INGEST_ENABLED=true` 기능 플래그 필요.
- Google Forms 공식 2026년 응답의 **실제 제출 ID + 본인에게 연결된 방문자 UUID + 제출 일시 + 품질결정**이 기존 공식 Apps Script 트리거에서 독립적으로 확인되어야 호출 가능.
- 제출 ID는 비공개 HMAC으로 변환하여 DB에 저장. 원본 ID/응답자 ID/설문 답변/인증 비밀키를 DB·로그·웹 응답에 출력하지 않음.
- **아직 기존 Google Form에 원본 응답자 방문자 매핑을 추가하지 않았으며, 이 초안이 실제 응답을 자동으로 인증하는 것은 아니다.** 실제 트리거/Forms 응답 필드와 연결하기 전에는 ingest 플래그를 활성화하지 않는다.

## 격리 검증

- `tests/challenge-2026-code-level-fixture.sql`: **합성** 방문자·고유번호(3가지 형식)·추천 품질검증 사건·기존 레벨코드 준비.
- `tests/challenge-2026-code-level-verify.sql`: 가상 DB에서 **발급만 된 코드 Lv0**, 서명된 원본 응답으로 비활성 코드 **Lv1**, 유효·품질 통과 추천 **Lv2**, 품질 보류/거부·비활성 추천에서 **Lv1 강등**, 본인 응답 철회 시 **Lv0**, 중복 응답 재사용 차단, 고유번호 변경 없음, 기존 레거시 Lv2 보존을 검증.
- `tests/v1.1.0-participation-code-levels.test.mjs`: 서버 라우트·원장·HMAC·승급 UI 정적 보안 계약.
- 기존 `tests/participation-code-unified.mjs`, `tests/levelup-provisional-v1.cjs`, `scripts/test-challenge-referral-premium.cjs`를 변경된 단계 규칙에 맞게 회귀 검증.
- `.github/workflows/v1.1.0-verified-challenge-code-levels.yml`: Deno Edge TypeScript, Node.js, 격리 PostgreSQL 16, 프리뷰 운영 DB/설문 격리 검사. 모든 테스트에는 실제 사용자 코드·설문 응답을 사용하지 않는다.

## 배포 차단 조건과 이행 순서

1. **4단계 운영 DB 암호화 백업 + 독립 복구 실제 검증**. 기존 5단계 Supabase Auth URL 설정 재검증도 별개로 필요.
2. 공식 Google Forms 응답(원본 Form response ID, 2026년 참여자 방문자 UUID)이 서버에서 **일대일로 검증 가능한 출처 연결**을 설계·설치하고, 구형 코드 발급자에 대해서도 증명 가능한 백필 대상만 별도로 식별할 것. **과거 2026 코드 전체를 일괄 승인하면 안 됨.**
3. 기존 유효 추천의 품질 기록 `AUTO_PASS`/`MANUALLY_APPROVED`와 실제 `credited` 사건을 병합 검증; 의심·반려·중복은 승인하지 않음.
4. 시험 DB에 새 마이그레이션을 안전하게 적용한 다음 별도 시험용 Google Forms 증명 잉제스트/서버 인증 기능을 연결, 인가된 합성 폼 제출 → Lv1 인증 → 추천 제출 → Lv2 승급 → 추천 철회 → Lv1 강등 → 본인 원본 응답 철회 → Lv0을 **실제 브라우저 E2E**로 확인.
5. 시험 환경과 운영 환경의 DB/서명키/Google Form 구분, 릴리스·수동 승인·롤백 확인 이후 운영 배포.
6. 새 검증 원장이 비어 있는 상태에서 새 API만 운영에 배포하면 **기존 2026 고유번호 전체가 Lv0로 떨어질 수 있다.** 반드시 증명된 레거시 응답 연결 이행·사전 집계·돌이킬 수 있는 배포 계획을 준비하고, 기존 정상 사용자의 불필요한 권한 소멸을 방지해야 한다.

**이 단계에서는 운영 DB·시험 DB/구글 설문지/운영·시험 웹 변경을 실행하지 않는다.** 코드 작성·독립 테스트는 실제 설문 연결 완료를 의미하지 않는다.
