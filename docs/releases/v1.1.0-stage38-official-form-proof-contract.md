# 배구지수 v1.1.0 · 38단계 공식 설문 제출 증빙 분리 설계

2026-11-22 확인. **검토용 코드·문서이며 아직 운영/시험 Supabase Edge Function, 실제 Google Form, Google Apps Script에 설치하지 않음.** 운영 웹·DB·설문 데이터·메인 브랜치에 변경 없음.

## 실제 확인한 현재 구현

- `scripts/beagu-2026-referral-integration.gs`의 `onBeaguReferralFormSubmitted(event)`는 소유자가 설치한 공식 Google Form 제출 이벤트와 선택형 **추천 확인코드** 문항을 검사한다. `BR1.`로 시작하는 유효한 추천 서명 코드가 없으면 즉시 반환하며, **일반 설문 제출의 본인 참여 확인은 백엔드로 기록하지 않는다**.
- `beagu-referral-ingest-v1`는 서버간 비밀키, 공식 응답 스프레드시트 식별자, Form 제출 ID·시각, HMAC 추천 증빙과 품질 신호를 검증한 다음 *추천인 공헌*만 처리한다. 이는 **자기 설문 참여 인증과 별개**다. Google Apps Script 트리거의 실제 설치/게이트 활성 상태는 이 코드 검사만으로 확인되지 않는다.
- `beagu_issue_challenge_identity`는 현재 Lv.1 이상 기존 세션을 요구한다. 신규 2026 설문 참여자의 Lv.1 코드 발급·인증으로 전용하려면 기존 Lv.1 선인증이 요구되는 **순환 의존**을 먼저 해소해야 한다.
- 운영 `beagu_private.challenge_identity_codes`는 발급만 기록하고, 제출 완료 검증 결과와 연결하는 독립 증명 컬럼/테이블은 없다. **발급·방문·체크인 이벤트 자체를 제출 완료로 간주하면 안 된다**.

## 제안하는 최소 증명 체계

핵심 규칙은 다음과 같다: **고유번호 발급 ≠ 설문 제출 완료 ≠ 유효한 추천 1건**. 2026 본인 설문 제출이 공식 Form 소유자 측에서 증명되고 고유번호 소유 관계까지 검증되어야 Lv.1이며, 추천 품질 심사를 통과한 독립 추천 1건으로만 Lv.2다.

1. 설문 제출 전에 로그인 권한이 없는 **사전 인증 대기 상태**를 별도로 둔다. 이 상태가 기존 Lv.1/Lv.2 API·포스트잇 접근권한을 제공하면 안 된다. 현재 `beagu-challenge-identity`의 Lv.1 선행 인증을 무단으로 제거하지 않는다.
2. 제출 증명은 실제 공식 Form의 **설치형 제출 이벤트**가 보낸 서버간 호출로만 수락한다. 응답 원문, Q01~Q13의 개별 보기, 이름, 이메일, 전화번호, 학교명, 자유 서술을 보낼 수 없도록 요청 필드를 엄격히 한정한다. 전송되는 원시 Form 응답 ID는 서버에서 즉시 별도 도메인 HMAC으로 해시 처리하고 원본을 저장하지 않는다.
3. 본인 참여 귀속은 추천 코드와 **완전히 별개의 선택적 동의·증빙 경로**로 구성한다. 가능하면 공식 Form 응답 열에 고정된 개인 고유번호를 남기지 말고, 단기·일회성 불투명 제출 증빙을 사용해 응답 원문과 고유번호의 장기 결합 가능성을 낮춘다. 어떤 방식이든 본인 고유번호와 제출 이벤트의 연결 가능성과 보존 기한에 대해 개인정보 영향 평가가 선행되어야 한다.
4. 서버는 공식 Form ID·응답 스프레드시트 ID·제출 이벤트 ID·시간·코드 형태·**서버 전용 공유 서명**을 확인한다. 서명만으로 브라우저 UUID나 코드를 소유한 사람의 신원을 확인했다고 간주하지 않는다.
5. DB 비공개 레지스트리에서 고유번호 발급 원장, 검증된 소유자/기기 바인딩, 중복 사용되지 않은 제출 이벤트, 별도 품질 판정을 모두 확인해야 한다. **원본 Form 응답 ID 및 교사 답변은 다른 서비스 테이블로 복제 금지**.
6. 필요 시 **Lv.1 인증**을 열되 기존 Lv.2 추천 증명은 그대로 엄격히 유지한다. `valid_referrals>=1`, `upgraded_at`, 코드 해시 일치, 비활성 상태 확인 및 증거 원천 검증이 없으면 Lv.2는 허용하지 않는다. 하나의 Form 응답이 본인 참여/추천 승급에 중복 가산되는 경계도 설계·검토해야 한다.

## 제출 증빙의 1회 귀속 및 동시 요청 경합 검증

2026-11-22 보완: 검토용 순수 함수의 `submissionUniquenessConfirmed` 입력은 그 자체로 영속 DB 원자성을 보장하지 않는다. **실제 중복 제출 방지에 필요한 원자적 증빙 소비 동작**을 별도의 일회용 PostgreSQL fixture로 검증했다.

- [합성 SQL](../../tests/stage38-synthetic-submission-claim-cases.sql)은 오직 GitHub Actions PostgreSQL 17 서비스에서만 실행된다. `stage38_claim_fixture` 비공개 테이블에서 `(event_digest PRIMARY KEY, code_digest UNIQUE)`를 함께 적용한다. 원본 Google Form 응답 ID, 고유번호, 설문 원문, 전화번호, 개인정보는 삽입하지 않는다.
- `stage38_claim_fixture.try_claim()`은 `SECURITY INVOKER`, `service_role` 단독 EXECUTE, RLS 활성화로 구성한다. 서버에서 **공식 Form 서명 검증·소유 관계 확인·재참여/동의 정책 검토를 마친 뒤**에만 호출해야 할 논리 예시다. 이 fixture 함수 자체는 서명을 검증하지 않으며 어떤 Lv.1/Lv.2 로그인 세션도 만들지 않는다.
- 실제 SQL 테스트에서 처음 제출만 성공하며, **동일 이벤트 재시도**, **동일 응답을 다른 코드에 귀속**, **한 코드에 다른 응답 중복 귀속**, **형식이 틀린 해시·NULL**은 모두 거부. 승인 조건을 누락해도 성공한 것처럼 처리하지 않는다.
- [일회용 PostgreSQL 스모크](../../tests/stage38-staging-login-foundation-smoke.sh)는 **분리된 DB 연결 2개로 동일한 합성 제출을 동시에 소비**시킨 후 성공 1회·거부 1회와 저장 건수의 불변성을 점검한다. 중간에 CI 스크립트의 결과 합산 오류를 발견해 수정했고, [릴리스 검사 #44991038609](https://github.com/noam0127/beagu-index/actions/runs/44991038609)에서 기본 검사와 PostgreSQL 검사 **둘 다 SUCCESS**.
- 테스트용 `event_digest`는 실제 구현 시 서버 전용 도메인 분리 HMAC으로 만들고 평문 Form ID/응답 ID를 영속화하지 않는다. `code_digest`와 증빙을 함께 보관하는 것 자체도 재식별 단서가 될 수 있으므로 **개인정보 보호 검토, 보존 기간·삭제 기준, 최소화 및 접근 감사**가 필요하다. 현재 실제 Form 연동은 이루어지지 않았다.

**중요:** 이는 중복 처리의 **DB 원자성만 검증한 합성 테스트**이며, 공식 Google Form 소유자 설치형 이벤트 검증, 임시 제출 토큰, 실제 소유 증명, 개인정보 영향 검토, 승인된 시험 Supabase 적용, Vercel 독립 RC 배포, 실제 로그인 E2E와는 별개다. **38단계 상태 미완료 / NO-GO.**


## 짧은 참여코드 HMAC 보호 및 재로그인 분리

2026-11-22 후속: 현재 10자리 Base32 참여코드의 엔트로피는 약 **50비트**로, 단순 SHA-256 지문만 저장하면 해시 유출 시 추측 공격에 노출될 수 있다. 이에 아직 **미배포 상태인** `scripts/release-manager/stage38-form-submission-evidence.mjs`의 참여코드 지문을 비밀키로 계산하는 **도메인 분리 HMAC-SHA256 (`BEAGU_ST38_CODE_V1|`)**으로 변경했다. 증빙 이벤트, 서명, 발급원장 비교 지문도 각각 용도를 구분한다. 검토 코드와 테스트 외 실서비스 저장/인증에 적용한 것이 아니다.

**최초 인증과 이후 로그인의 역할을 분리**한다.

1. **최초 등록 시:** 공식 설문 HMAC 증빙, 발급 원장과 검증된 소유 관계, 단일 응답의 미사용 여부를 확인하고 비공개 DB에서 원자적으로 제출 증빙을 소비한다. 실제 권한 부여는 별도 승인된 서버 기능으로만 한다.
2. **이후 로그인 시:** 동일 공식 설문 응답을 다시 제출하거나 소비하지 않는다. 이미 적법하게 등록된 증빙과 현재 발급원장의 활성 상태를 **읽기 전용**으로 조회한다. 그러나 이 상태 조회만으로는 로그인 불가하며, 실제 코드 소유 확인·호출 제한·기기/계정 정책을 서버에서 별도로 검증해야 한다.
3. **철회 시:** 발급원장 `active=false` 또는 별도 이용정지 정책이 적용되면 반복 조회도 실패해야 한다. 단순 중복 제출 방지 때문에 정당한 이후 로그인을 거부해서는 안 된다.

[일회용 PostgreSQL 전용 테스트](../../tests/stage38-synthetic-submission-claim-cases.sql)의 `stage38_claim_fixture.has_active_enrollment()`은 위 **읽기 전용 조회**만 검증한다. 원자적 소비가 이미 성공한 코드는 3번 반복 조회할 수 있지만, 발급되지 않은 코드·참여는 했으나 등록 증빙이 없는 코드·잘못된 해시·철회된 코드는 거부한다. 이 함수는 시험/운영 Supabase에 설치되지 않았고 **실제 세션을 만들지 않는다**. 합성 SQL에 쓰이는 일반 SHA-256 해시는 가짜 문자열에 한정되며 실제 고유번호용 지문 구현이 아니다.

**CI 실제 결과:** [Site release manager checks #44991448377](https://github.com/noam0127/beagu-index/actions/runs/44991448377)에서 정적·Node 증빙 7개·독립 PostgreSQL 17 스모크 두 작업 **모두 SUCCESS**. 중간에 테스트 파일의 JS 문자열 치환 처리 오류로 SQL이 손상된 것을 발견했고, 정상 소스에서 재구성해 다시 전체 검증을 통과했다.

보안상 남은 주요 과제: HMAC 비밀키 생성/보관/회전 및 서로 다른 증빙 지문의 일관된 재키잉, 비공개 제출 증빙의 보존 기간과 삭제 정책, 공식 Google Form 제출 및 소유자 승인 연결, 실제 테스트 Supabase 경로와 보안 등급별 브라우저 E2E. 모두 완료 전까지 **38단계 NO-GO**.


## 인증용 비밀키 교체·유예·폐기 정책 (검토용 v2)

2026-11-22 후속 검토. 기존 `stage38-form-submission-evidence.mjs`의 단일 비밀키 참조 구현에 **버전 2 봉투(envelope) 방식의 키 교체 검증 기능**을 추가했다. 새 코드도 **Google Form/Apps Script/실제 Supabase에 연결하지 않은 검토용 Node 코드**다.

- 서명 봉투는 `{version:2,keyId,signature}` 형식. 비밀키·응답 ID·고유번호·문항 응답은 봉투에 포함하지 않으며, 버전/키 번호도 HMAC 계산에 반영한다. 키 번호가 변경되거나 서명이 수정되면 검증 실패한다.
- 키 원장은 정확히 **하나의 active** 키를 가진다. `active`만 새 이벤트에 서명하고, `verify-only`는 반드시 **명시적 만료 시각**이 있어야 과거 서명 검증에 사용할 수 있다. `revoked`·없는 키·유예기간 종료 키는 일절 검증하지 않으며 활성 키로 임의 fallback하지 않는다.
- 비밀키는 길이가 충분한 서버 전용 고엔트로피 값이어야 한다. 이 검토용 모듈은 하드코딩된 테스트 가짜값을 제외하면 **어떠한 비밀키도 저장·발급·노출하지 않는다**. 운영 연결 시 서버 키 관리, 최소 권한, 접근 감사, 유실·침해 대응/비상 폐기 절차를 별도 구현해야 한다.
- 버전 2 키에서는 도메인 분리 HMAC으로 참조 프로토콜용 키를 도출한다. 기존 v1 형식의 서명·영수증을 무조건 받아들이는 다운그레이드 fallback은 없다. 키 원장의 잘못된 설정, 중복 비밀키, 둘 이상의 active 키, verify-only 만료 시각 누락은 즉시 거부한다.
- **코드 지문도 키별로 달라진다.** 실제 발급 원장·증빙 원장에는 어떤 키로 생성했는지 기록할 수 있어야 하며, 과거 키 지문을 현재 키의 지문이라고 단정하거나 새 키로 자동 재해시할 수 없다. **기존 합법적 등록·이후 재로그인은** 검증 완료된 비공개 등록 상태를 기준으로 하되, 별도의 실제 코드 소유 확인·폐기 상태 확인·로그인 시도 제한이 필요하다. 과거 서명 키가 폐기됐다고 이미 합법적으로 등록된 사용자 상태를 무조건 삭제한다는 뜻은 아니다.
