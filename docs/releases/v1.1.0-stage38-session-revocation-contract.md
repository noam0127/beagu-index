# 배구지수 v1.1.0 · 38단계 세션 실시간 철회 검증 계약

2026-11-22 · **아직 배포하지 않은 서버 전용 참조 구현 및 테스트 명세.**
운영·시험 Supabase 데이터/스키마, 실제 Google Form, 운영 웹, Vercel 프리뷰와 GitHub `main`은 이 작업에서 변경하지 않았다.

## 운영·시험 API를 읽기 전용으로 확인한 문제

2026-11-22에 실제 배포된 양쪽 `beagu-level-api`의 **코드**를 읽어 확인:

- `login`은 `beagu_level_codes`의 `active=true`를 확인하여 고유번호를 검증하지만, 발급된 `beagu_level_sessions` 기록에는 해당 코드의 식별자가 들어가지 않는다. 기본 유효기간은 **6시간**이다.
- 이후 `verify`와 다른 보호된 API 동작에서 공통 `check(req)`는 세션 토큰의 SHA-256과 만료일, 그리고 **추천으로 획득한 2026 Lv.2**의 `beagu_has_earned_challenge_visitor`을 검사한다.
- 즉 추천 실적 기반 Lv.2는 추천 프로필 비활성화 시 보호된 API에 대한 다음 요청부터 차단하는 구조이나, **기존 참여코드 테이블을 통해 발급된 세션**은 코드 자체가 나중에 `active=false`가 되어도 현 `check`에서 원래 코드의 상태를 재확인할 자료가 없다. 다음 요청에서 곧바로 철회되었다고 주장할 수 없다. 단, 이미 만료된 세션이나 로그아웃 세션 등은 기존 동작대로 거부된다.
- 이 차이는 기존 운영 API의 **현재 동작 분석**이지 이 단계에서 운영 코드를 수정했다는 뜻이 아니다.

## 승인된 시험 환경에 향후 구현할 계약

**범위:** 개인정보와 설문 원본을 DB에 복제하지 않은 2026의 *신규* Lv.1/Lv.2 참여코드 인증 세션이다. 기존 레거시 코드 세션을 검증되지 않은 규칙으로 한 번에 중단하지 않는다.

1. 정식 설문 참여 증빙의 일회성 수락과 **재로그인을 위한 읽기 전용 회원 등록 조회**를 분리한다. 서버 전용 고유번호 조회용 HMAC 키를 사용하며 실제 참가 코드 문자열은 세션 테이블에 저장하지 않는다.
2. 신규 `beagu_level_sessions`에 `identity_campaign=2026`, `code_lookup_key_id`, `code_lookup_digest`, `access_level`, `created_at`, `expires_at` 등을 코드와 연결해 저장한다. **세션 토큰 원문은 저장하지 않고 강한 난수 토큰의 해시만 저장**한다.
3. 별도 **비공개·RLS 활성화 회원 등록 원장**에는 `campaign`, `lookup_key_id`, `code_lookup_digest`, `proof_state=claimed`, `evidence_origin=official-signed-form`, `owner_binding_state=verified`, `active`, `revoked_at`, 검증된 등급과 필요 시 방문자 식별자를 포함한다. 이 필드는 설문 응답과 개인을 직접 연결하는 비밀 증빙이므로 개인정보 영향 검토, 최소 보존 기간 및 접근 감사가 선행되어야 한다.
4. 보호된 요청 시마다 신뢰할 수 있는 서버가 세션 토큰을 조회하고, 같은 캠페인/조회키 ID/HMAC 지문으로 **현재 활성 상태·철회 여부·원천 증빙·소유 확인·등급**을 다시 확인한다. 영속 원장 조회에 실패할 때는 권한을 부여하지 않는다. 단순 클라이언트의 `active=true`나 `ownerBindingVerified=true` 주장만 받아서는 안 된다.
5. 세션의 원래 등급보다 높은 등급을 **기존 토큰에 자동 부여하지 않는다.** 반대로 원장 등급이 내려가거나 코드가 철회된 경우, 높은 등급의 오래된 세션은 다시 인증받기 전까지 실패한다. Lv.2는 추천 실적 RPC의 **현재 유효 상태**와 방문자 식별자 일치가 추가로 필요하다. Lv.3는 여전히 별도의 Auth 계정·연결·상태 검사가 필수다.
6. 세션의 기본 유효기간은 6시간 이내이며 만료/미래 발급 시각/비정상 날짜/기간 초과를 거부한다. 만료된 토큰의 해시 및 사용 완료 증빙은 개인정보 보존 정책에 따라 별도로 정리한다.

## 수행한 작업과 검증 범위

- `scripts/release-manager/stage38-session-revocation-policy.mjs`에 서버에서 이미 **신뢰할 수 있는 DB 조회를 수행한 후** 적용할 순수 참고용 권한 판정 로직 `effective2026ProtectedTier`을 구현했다. 이 코드는 실제 Edge Function에 연결되지 않아 어떤 계정·세션도 발급하지 않는다.
- `tests/stage38-session-revocation-policy.mjs`에서 가짜 기록만 사용해 **정상 Lv.1, 코드 철회 즉시 거부, 위조 세션/미검증 코드, 만료/시간 오류, 2026 Lv.2의 현재 추천 인증, 승급/강등 정책, 읽기 전용 반복 호출**을 검사한다.
- GitHub Actions `site-release-manager-validation.yml`에 자동 검증을 연결했다. **GitHub CI 성공은 원본 `beagu-level-api`를 실제 수정하거나 브라우저/E2E를 통과했다는 뜻이 아니다.**

**판정:** 38단계 미완료(실제 시험 DB 합성 마이그레이션·독립 Vercel RC 배포·실제 브라우저/Auth/RLS·관리자 승인 필요). 운영 웹과 개인정보 데이터베이스 변경 금지.


## 일회용 PostgreSQL 실제 관계형 세션 철회 검증

2026-11-22에 `tests/stage38-synthetic-session-revocation-db.sql`을 생성하고 릴리스 검증의 **GitHub Actions PostgreSQL 17.6 독립 서비스 컨테이너**에 연결했다. 이 SQL은 프로젝트가 아닌 일회용 DB `postgres`와 `stage_private` 가짜 테이블, `app.stage38_fixture_only='ephemeral-ci'`, 운영 전용 테이블 부재를 확인하지 못하면 실행이 중단된다. **실제 시험/운영 Supabase에 적용되는 마이그레이션이 아니다.**

실제 관계형 `stage38_session_fixture.sessions`와 `stage38_session_fixture.enrollments`을 합성 데이터만으로 생성한다. 양쪽 모두 RLS를 활성화하고 공개 `anon`/`authenticated` 접근권한을 철회했다. `service_role`만 이용 가능한 `SECURITY INVOKER`의 **읽기 전용 `protected_tier(token_sha256)`**가 세션·등록 상태·등급·소유 증명·현재 추천 상태를 결합해 권한을 판정한다. 세션 토큰은 가짜 SHA 지문으로만 표현하며 실제 고유번호·응답 ID·전화번호·원시 설문 데이터는 없다.

테스트 상황은 기존 세션 5개와 합성 등록 3개를 만든 뒤 다음을 순서대로 확인한다.

- 정상 Lv.1·유효 Lv.2만 각각 1·2를 반환. 설문 증빙 없이 발급만 된 코드, 세션-코드 키 불일치, 만료/존재하지 않는 세션, 불량 토큰 지문은 거부
- 세션 유효기간이 남아 있어도 **기존 등록 원장을 `active=false`, `revoked_at=now()`로 바꾸면 바로 다음 조회에서 Lv.0**
- Lv.2 추천 유효 상태를 `earned_lv2_now=false`로 바꾸면 **이전 Lv.2 토큰도 바로 다음 요청부터 거부**
- Lv.2 등록을 Lv.1로 강등하면 **이전 Lv.2 토큰을 Lv.1로 자동 재사용하지 않고 다시 로그인하도록 거부**
- 판정 과정에서 저장된 세션·등록 건수는 변하지 않으며, 권한 판정이 자체적으로 로그아웃·세션 발급·개인정보 복제를 하지 않음을 확인

**검증 범위:** 임의의 사용자 요청에 대한 HTTP 인증을 실행한 것은 아니며, 서버가 먼저 강한 난수 베어러 토큰을 검사해 `token_sha256`을 계산하고 DB를 호출해야 한다. 운영 중인 `beagu-level-api`는 여전히 레거시 코드 세션의 즉시 철회를 구현하지 않는다. 이 실험을 통한 권한 규칙 확정은 **장래 승인된 시험 Edge Function·마이그레이션의 설계 근거**로만 사용한다. 개인정보·보존기간·기존 사용자 호환성을 검토하기 전에는 실제 DB를 변경하지 않는다.
