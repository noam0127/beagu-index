## 관리자가 별도 명시적으로 승인할 때만 진행할 순서

1. **사전 변경 심사.** PR #243 변경 파일이 8개(관리자 HTML/CSS/JS, 릴리스 함수+공유 검사, 오프라인 보안 테스트/CI)인지 확인. 현 `main` HEAD, Edge 함수 v3 소스·설정, 배포 관리 DB의 `production_sha`/`staging_sha`를 백업·기록. 아직 PR #195를 병합하지 않음.
2. **부트스트랩 승인을 분리.** 관리자와 운영자가 PR #243의 **작은 컨트롤러 패치**를 승인할 때만 해당 PR을 draft에서 해제하고 리뷰·병합. **승인 전 임의 병합 금지.** PR 병합만으로 운영 Edge 함수가 업데이트되지는 않으며 새 관리자 UI도 자동 적용됐다고 간주하지 않음.
3. **배포 API 호환성 설치.** 별도 승인된 방법으로 새 `beagu-release-manager-v1` Edge Function과 `_shared/staging-release-candidate.mjs`를 함께 배포. 이전 v3 백업 유지. 기존 `status` / `register` / `stage_apply` / `worker_*` 계약이 파손되지 않았는지, AAL1·위조 토큰은 계속 403인지 확인. 이 단계에 절대 RC 웹사이트를 운영 배포하지 않음.
4. **관리자 UI 부트스트랩.** 기존 관리자 AAL2로 **승인받은 작은 컨트롤러 변경만** `main`의 정확한 커밋·예: `1.0.2-controller-bootstrap`이라는 별도 비RC 버전으로 등록 → 시험 웹 적용 → 프리뷰 관리자 화면/수동 회귀 확인. 운영 관리자 화면에도 반영이 필요하면 **이 부트스트랩 패치에 한해서** 별도의 관리자 승인 후 적용. 승인 없이 실제 웹으로 승격하지 않음.
5. **RC 시험 배포 승인.** 새 관리자 UI에서 진짜 **소유자 AAL2** 로그인으로 `release/v1.1.0-rc.1`의 고정 SHA `5c95aadad971901a8222f83c52e93bf901a3aeb7`를 **시험 전용으로 등록**. `draft_sha`와 SHA·버전이 일치하는지 확인하고 **시험 웹 적용** 버튼을 관리자 본인이 승인. 이 때 GitHub Actions가 서명된 작업을 가져가야 하며 직접 작업 테이블을 INSERT/UPDATE하지 않음.
6. **실제 적용 증빙.** GitHub Pages 배포 완료, DB `beagu_site_release_jobs_v1.status='deployed'`, `beagu_site_release_history_v1`의 해당 SHA/버전, `beagu_site_release_state_v1.staging_sha`가 고정 SHA와 **모두 일치**한 다음 `https://baeguindex.com/_preview/`와 개별 JS/CSS의 HTTP 200·프리뷰 워터마크·시험 Supabase URL·읽기 전용 권한 동작을 검증.
7. **38단계 종료 또는 실패 판정.** 모든 지표와 실서비스 시험이 입증된 경우에만 `38단계종료`. 하나라도 충족되지 않으면 `38단계 진행 중`. 2026 실자료·메일·AAL2 양성 시험 등 36단계 운영 출고 차단 조건은 여전히 남으므로 **v1.1.0 RC를 실제 웹에 적용하면 안 됨**.

## 중단·복원 조건

- 정식 AAL2 사용자 세션 없음, 새 릴리스 함수 응답 오류, PR 변경 범위 확대, RC 브랜치 SHA 이동, 작업자 워크플로 실패 또는 게시된 SHA 불일치 → **즉시 설치 및 승격 중지**.
- 부트스트랩 시험 웹 적용 실패 → 관리자가 이전 시험 배포 이력·SHA로 롤백, GitHub Actions 결과·도메인 비교 후 원인 검토.
- 부트스트랩 Edge 배포로 기존 관리 API가 손상되면 → 사전에 백업한 Edge v3를 **승인된 운영 절차로만** 재배포하고 기존 로그인·배포 조회 정상 확인.
- 부트스트랩 운영 UI가 이미 관리자 승인으로 배포된 뒤 장애가 나면 → 그 UI 패치만 별도 승인된 `prod_rollback`으로 복구. 운영/시험 SHA 일치 및 회귀 검사 전 다른 변경을 진행하지 않음.
- **임의 수단 금지:** MFA 우회, 임의 관리자를 생성해 배포 버튼 클릭, 운영 DB 릴리스 상태 직접 변경, RC를 `main`에 병합, 운영 웹을 GitHub Pages에서 강제 덮어쓰기.

**38단계 6/6차 인계 결과:** 필요한 개발 코드·PR·정적/격리 HTTP 테스트·순서·롤백 판단 기준은 준비됨. **마지막 필수 작업인 실제 소유자 AAL2 승인/웹 배포는 미실행**이므로 38단계 종료를 선언하지 않음.


## 2026-11-22 추가 필수 조건: 시험 백엔드 분리 워커

실제 운영 `main` 배포 워커는 `_preview`에 워터마크만 삽입하고 운영 Supabase 주소/공개키를 교체하지 않는 것으로 확인했다. **부트스트랩 PR #243만 설치해 RC를 시험 배포하는 것은 금지한다.** 같은 URL 경로에서 시험 브라우저가 운영 API에 요청할 위험이 있기 때문이다.

- 분리 패치: [Draft PR #244](https://github.com/noam0127/beagu-index/pull/244) — `hotfix/v1.1.0-preview-backend-isolation`, 파일 3개. 운영 메인과 분리된 개발용 리뷰 PR이며 자동 병합되지 않았다.
- [GitHub Actions #44983523157](https://github.com/noam0127/beagu-index/actions/runs/44983523157): 기존 승인·보안·오프라인 패키징/2-SHA 회귀 **success**. 운영 Supabase 주소·공개키가 시험 정적 자산에 남으면 패키징을 실패시키고, production 고정 SHA 아티팩트는 불변으로 유지.
- **변경된 승인 순서:** PR #244 보안 리뷰·기존 워커 백업·명시적 운영자 승인과 적용 → PR #243 컨트롤러/API·UI 승인 및 적용 → 소유자 AAL2 인증 후 RC 등록·시험 `stage_apply` → 실제 시험 브라우저의 API 요청 도메인·Auth 저장소·쓰기 권한·2026 정보공개 E2E 확인.
- URL rewrite는 코드 상의 직접 하드코딩 참조를 낮추는 조치이며, `_preview`가 본 사이트와 **동일 출처(path만 구분)**라는 점을 완전한 브라우저 보안 격리로 해석할 수 없다. 실제 브라우저·CSP·로그인 세션·쿠키/Storage 및 시험 API 접근 통합 검증을 마치기 전에는 민감 자료를 사용하는 QA를 금한다.
- 이번 인계 문서 수정 및 PR #244 생성은 운영 웹, 운영/시험 Supabase, `main`, 고정 `v1.1.0-rc.1` SHA를 변경하지 않는다. 38단계는 계속 `BLOCKED_ON_OPERATOR_APPROVAL` 및 출고 NO-GO.
