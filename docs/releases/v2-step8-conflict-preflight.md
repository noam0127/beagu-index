# 배구지수 통합 업데이트 시스템 v2.0 · 8단계 충돌 위험 사전 검사

2026-11-22 (KST) · 개발 브랜치 전용 · **운영 웹/시험 웹/운영 Supabase 미배포**

## 왜 필요한가

여러 ChatGPT 채팅방이 동시에 개발한 PR을 한 번에 합치려면 **실제 병합 전에 위험 영역을 찾아야 한다.**
6단계 PR 의존성 확인, 7단계 PR 수정 파일·CI 증빙 수집 결과를 그대로 재사용한다.
사전 검사가 통과하더라도 Git 3-way 병합 또는 전체 통합 테스트가 통과했다는 의미는 아니다.

## 8단계에서 구현한 분석

관리자 'PR 수정 파일·충돌 위험 사전 검사' 버튼을 눌러 다음 순서로 분석한다.

1. GitHub PR 목록의 열린 작업 중 **최대 6개**를 선택해 head SHA와 수정 파일·개별 CI 기록을 조회한다.
2. PR 두 개씩 짝지어 변경 파일의 **정확한 동일 경로**를 비교한다.
3. 다른 파일이라도 **동일 Supabase Edge Function 디렉터리**를 수정했다면 인증·API 계약 검토 대상으로 분류한다.
4. 서로 다른 SQL 마이그레이션을 가진 PR 두 개는 'DB 변경 병행'으로 분류한다.
   파일명만으로 **같은 테이블 수정이라고 단정하지 않으며**, 마이그레이션 순서·RLS·컬럼 의존 관계는 SQL 본문을 확인해야 한다.
5. 배포·CI 설정이나 공개 데이터 파일을 양쪽에서 각각 바꿨다면 관련 정책의 교차 점검을 요구한다.
6. PR의 head SHA가 같거나, 선행 PR 브랜치를 기반으로 했다는 사실을 발견하면 중복 또는 stacked 작업 여부를 안내한다.
7. 한 쪽이라도 수정 파일 조회가 실패·일부만 수집·SHA가 유효하지 않으면 **검사 불완전**으로 처리한다.
8. 동일 파일 수정이 보이지 않더라도 '사전 관찰에서 중복 위험 미발견'으로만 표시한다. **병합 가능·통합 완료·운영 배포 승인이라고 표시하지 않는다.**

## 실제 확인된 사례

PR #193과 #199는 `supabase/functions/beagu-release-manager-v1/index.ts`,
`tests/site-release-center.mjs`를 함께 수정한다. 별도의 Node 테스트에서 이 동일 파일 변경을 탐지한다.
PR #195와 #199는 `scripts/release-manager/worker.py`와 `tests/site-release-packaging.py`에 수정이 겹친다.
이 검사는 **파일 충돌 위험**을 알려줄 뿐 실제 Git conflict 여부는 9~11단계의 임시 통합 브랜치에서 검증한다.

## 화면과 API 처리

- 관리자 Owner+AAL2의 `status(check_latest=true, inspect_work=true)`만 추가 분석을 실행한다.
- 7단계의 `impact`에서 가져온 수정 파일 정보를 메모리에서 비교하고 `work_inbox.conflict_preflight`로 반환한다.
- 각 쌍의 PR 번호, 공통 수정 파일, 위험 분류, 오류 및 분석 누락 상태를 표시한다.
- 자동 상태 새로고침은 추가 GitHub API 호출을 하지 않는다. 사용자가 검사 버튼을 누를 때만 분석한다.
- 분석 범위의 제한(열린 PR 최대 6개)과 잘린 파일 목록은 **분석 불완전**으로 보여준다.
- CI 결과는 각 PR의 독립 검사 결과일 뿐, 합쳐진 코드에서의 테스트 통과 증빙이 아니다.
- 수정 파일은 경로만 검사하므로 SQL 테이블 수준 의존성, 동일 함수 내부의 의미적 충돌,
  화면상의 상호작용 오류는 후속 단계에서 실제 코드를 결합한 다음 검사해야 한다.

## 절대 금지

- PR 병합 또는 `main` 수정
- 운영/시험 GitHub Pages 배포
- 운영 Supabase SQL/Edge Function/설문 데이터 변경
- 사전 검사만으로 버전 생성·운영 배포 승인
- 복구할 코드 SHA가 없는 롤백을 정상적인 '전 버전 복원'이라고 안내

## 후속 단계

- **9단계:** 선택된 PR을 선행 관계와 SHA로 고정해 별도의 통합 브랜치에서 실험적으로 조합.
- **10단계:** Git 3-way merge 충돌을 실제로 발견·해결, 변경 의도 차이와 DB/Edge API 충돌 검토.
- **11단계:** 전체 통합 CI, 보안·DB·E2E 테스트 수행. 실패하면 출시 후보로 인정하지 않음.
- **12단계:** 성공한 통합 커밋 SHA를 변경 불가능한 버전으로 등록.
- **후속 배포 단계:** 독립 시험 웹에서 검증하고 적용 진행 막대기·롤백 대상 SHA 확인 후 관리자가 별도 운영 배포 승인.
