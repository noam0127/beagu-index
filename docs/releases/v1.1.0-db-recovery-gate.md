## DB 변경 전 실제로 충족해야 하는 복구 기준

1. 운영 Supabase Dashboard → Database → Backups에서 사용 가능한 실제 스냅샷/복구 지점을 먼저 확인합니다. Free 플랜의 백업이 있다고 가정하지 않습니다.
2. 스냅샷이 없다면 **소유자가 신뢰하는 로컬 PC 또는 제한 접근되는 비공개 환경**에서 Supabase CLI `supabase db dump --help` 또는 PostgreSQL 17 `pg_dump`를 사용하여 **암호화된 오프사이트 논리 백업**을 생성합니다. DB URI·암호·Auth 토큰을 공개 GitHub, 채팅, CI 로그에 기록하지 않습니다.
3. `auth`, `public`, `beagu_private`, 그 밖의 실제 사용 스키마, 데이터/권한/마이그레이션 및 함수와 스토리지 객체의 독립 보존 여부를 확인합니다. Supabase 관리형 DB 백업만으로는 스토리지 파일 본문이 복원되지 않을 수 있습니다.
4. 백업 파일에 SHA-256 체크섬, 생성 시각(UTC), Postgres/CLI 버전, 제외 범위, 소유자만 접근 가능한 보관 위치를 기록합니다. 공개 저장소에는 **경로/암호/파일 자체를 올리지 않습니다.**
5. `pg_restore --list` 등으로 파일 구조를 확인하고 **운영과 완전히 분리된 DB**에 시험 복구하여 대표 테이블 건수·제약조건·RLS/인증 데이터의 무결성을 확인합니다. 복구 테스트 전에 대상 DB가 운영 DB와 다름을 강제 검증합니다.
6. 성공한 백업/복구의 증거만 저장소의 **PII 없는 요약**으로 기록하고 `v1.1.0-rollback-baseline.json`의 `database.recovery_export_verified`를 true로 전환합니다.
7. 그때까지 **운영 DB 쓰기, 마이그레이션, 리셋, 파괴적 변경, 실제 계정 생성·실험을 차단**합니다. 클라이언트-only 변경이라도 서버 설정을 바꾸려면 별도 승인·검증 절차를 따라야 합니다.

## Git 코드 롤백 사전 검증

- GitHub Actions [`#44902905133`](https://github.com/noam0127/beagu-index/actions/runs/44902905133) 성공: 운영 소스 `index.html`, `CNAME`, `js/supabase-config.js`를 지정 SHA로 복구한 결과가 원래 blob과 **바이트 단위 일치**.
- 시험 소스는 `/_preview/` 대상으로 빌드하고 Stage 3 격리 CSP/시험 Supabase 라우팅 검증을 통과.
- 잘못된 SHA를 주입하면 빌드가 실패하는 것도 확인.
- 이 테스트는 **실제 운영 환경 배포/롤백도, DB 복원도 실행하지 않은** 오프라인 드라이런입니다.
- 기존 `beagu-release-manager-v1`의 운영 롤백은 DB 이력 `from_sha`를 이용하며 **최초 `bootstrap` 기록의 `from_sha`가 NULL**인 현재 상황에서는 관리자 UI의 `prod_rollback`이 작동하지 않습니다. 37~42단계 전에 롤백 기준/이력/승인 체계를 추가 검증해야 합니다.
