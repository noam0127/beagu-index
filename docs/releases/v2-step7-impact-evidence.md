# 배구지수 통합 업데이트 시스템 v2.0 — 7단계: PR 수정 영향·CI 증빙 분석

작성: 2026-11-22 · **PR #205 위에 쌓은 개발 브랜치, 운영/시험 배포 금지**

## 목표와 실제 구현

각 채팅방의 GitHub PR을 한 번에 통합하기 전 수정된 코드 범위와 검증 증빙을 읽기 전용으로 확보한다.
6단계의 PR 의존성 그래프를 보존하며 다음 항목을 추가했다.

1. 관리자 업데이트 화면의 **PR 수정 파일·테스트 증빙 분석** 버튼에서 `status(check_latest=true,inspect_work=true)`를 호출한다.
2. Owner+AAL2 세션의 Supabase Edge Function이 GitHub API의 `/pulls/{number}/files`와 `/commits/{head_sha}/check-runs`를 조회한다.
3. 파일 경로를 검증하고 중복 파일을 제거한다. 변경 수/추가·삭제 라인 수/파일 종류별 합계를 보여준다.
4. 변경 파일을 DB 마이그레이션, Edge Function, GitHub Actions·배포, 시험 코드, 화면, 공개 데이터, 문서, 기타 코드로 구분한다.
5. 영향받는 기능의 검증 필요성을 표시한다. DB 변경이 감지되면 스키마·RLS 검토, Edge Function 변경이면 인증·권한 점검, UI면 브라우저 회귀 검사를 요구한다.
6. CI 기록은 **PR의 정확한 head SHA와 일치하는 실행**만 표시한다. 성공, 실패, 진행 중을 구분하지만 PR 하나의 성공만으로 통합 성공을 주장하지 않는다.
7. GitHub API가 실패하거나 파일/CI 목록에 잘림이 생기면 `partial` 또는 `unavailable`로 표시하여 빈 항목이나 성공으로 오인하지 않도록 한다.
8. 상태 자동 새로고침이 GitHub API 호출을 과도하게 만들지 않도록 분석은 **명시적 버튼 조작 때만** 수행하며, 최신 열린 PR **최대 6개**, 파일 목록 **최대 3페이지**, CI 확인 **최대 100개**로 제한한다. 나머지는 `not_scanned`으로 표시한다.

## 통합 단계 안전 원칙

- 파일 경로가 중복된 PR은 실제 3-way 병합에서 충돌이 생기는지 아직 확정할 수 없다.
  **8단계에서 겹치는 파일을 탐색하고, 9~11단계에서 실제 병합·테스트**를 실행한다.
- 수정 파일의 존재 자체를 '구현 완료'의 증명으로 취급하지 않는다.
- CI 성공 몇 건을 확인하더라도 검사 항목이 충분한지, 브라우저나 DB 통합 기능이 정상인지는 아직 모른다.
- DB 마이그레이션 파일 탐지는 **운영 DB에 적용한 것이 아니다.** 어떤 SQL을 실행하는지도 파일 이름만으로 확정할 수 없다.
- Edge Function 파일 변경 탐지는 **그 함수를 배포했다는 뜻이 아니다.**
- GitHub에서 403/429로 제한되는 CI 조회는 그대로 '증빙 조회 불가'로 표시한다.
- 사용자 데이터·운영 Supabase·운영 웹·시험 웹에는 **조회 외의 변경을 하지 않는다.**
- PR #193→#201→#205→이번 7단계 PR의 스택을 유지한다. #198/#199/다른 작업은 9~11단계에서 별도 통합·검증한다.

## 이어서 필요한 후속 구현

- 8단계: 선택한 PR 사이의 **중복 파일·스키마·API·배포 워크플로 영향** 사전 충돌 위험 분석. 현재는 PR별 파일 분류에 집중.
- 9~11단계: 선행 PR을 포함해 임시 통합 브랜치 생성, 실제 3-way merge, 최종 DB/함수/브라우저 회귀·보안 테스트. 실패 시 버전 생성 불가.
- 12단계: 검증된 통합 SHA를 불변 릴리스 버전으로 확정.
- 배포/롤백 단계: 시험·운영 배포 상태 진행 막대기와 복구 대상 SHA가 없는 첫 시험 롤백 방지.

## 범위 제한

이 PR은 실제 코드를 변경한 **개발 결과**이지만, 운영 서비스에 설치하지 않는다.
현재 PR #193의 릴리스 카탈로그 DB/Edge Function 자체도 운영 환경에 미적용 상태이므로
운영 관리자 화면에서 즉시 이 버튼을 사용할 수 없다.
