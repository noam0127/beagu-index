# 배구지수 v1.1.0 — 18단계: Lv2 고유번호 소유권 + 인증된 Auth 계정 독점 연결

**2026-11-22. 상태: 개발 브랜치 코드·격리 PostgreSQL 16 자동 검증 완료. 실제 Lv3 인증/권한 부여·운영 DB 마이그레이션·실제 계정 E2E·시험/운영 웹 배포 미실행.**

## 왜 별도의 서버 연결 기록이 필요한가

참여코드는 복사·전달할 수 있는 문자열이다. **코드 소지나 브라우저의 Lv2 표시만으로 정식 회원 계정 소유권을 증명할 수 없다.** 한 사람이 여러 이메일 계정을 만들어 하나의 추천 실적을 재활용하거나, 다른 사람의 추천코드를 입력해 회원 등급을 받을 가능성을 차단해야 한다.

기존 시스템에는 다음이 이미 있었다.

- 2026년 참가자의 고유번호, 참가자 UUID, 원래 기기에 연결된 `challenge_device_claims.device_secret_sha256`.
- 이메일 인증·비밀번호/Google 로그인을 담당하는 Supabase Auth.
- 2026년 원본 설문 검증과 품질검토가 통과한 추천 1건을 요구하는 **17단계 서버 권한 판정**.
- 포스트잇 작성자 연결 기록 `public.beagu_postit_member_accounts` 및 `beagu_postit_bind_verified_member`. 다만 기존 연결 함수는 본인 설문 완료 검증과 현재 Auth 로그인 세션 재검증을 별도 수행하지 않았으며, 다른 계정 서비스가 이 연결을 Lv3 권한으로 사용해서도 안 된다.

## 구현 결과

### 1. 원자적인 1:1 연결 원장 + 감사 이력

`supabase/migrations/20261122001000_beagu_lv3_verified_account_link_v1.sql`

- `beagu_private.member_lv3_identity_links_v1`: **회원 Auth UUID 고유 / 2026 참가자 UUID 고유 / 포스트잇 작성자 UUID 고유**. `linked/suspended/revoked` 상태. 단일 고유번호 다중 계정 연결, 단일 계정의 여러 번호 연결 불가.
- `beagu_private.member_lv3_link_events_v1`: 최초 성공 시 UUID와 시각·연결 이벤트만 기록. 재요청은 동일 결과로 처리하고 기록 중복 없음. 계정 이메일, 비밀번호, 고유번호 원문, 기기 비밀값, 응답 원문·JWT는 저장하지 않음.
- 두 비공개 테이블에 RLS 활성화, 공개 역할(`anon/authenticated`) 직접 읽기/쓰기 금지. 기존 API에서 사용할 보안 RPC 역시 `service_role`에게만 EXECUTE.
- **기존** `beagu_postit_bind_verified_member(p_user,p_visitor,p_device_hash,p_actor)` 시그니처 유지. 한 트랜잭션 안에서 원래 작성자 기록과 별도의 향후 Lv3 연결기록을 함께 저장. 다른 계정의 참가자 소유권 또는 이미 정지/철회한 연결을 덮어쓰지 않음. 동시 접근 시 유일 제약으로 중복·도용 충돌을 차단.
- DB에서도 확인하는 필수 조건: 인증된 비익명 Auth 계정, 발급된 2026 방문자, **본인 설문 검증 + 유효 추천 + 품질 승인으로 산출된 현재 서버 Lv2**, 정확히 기존 기기에 기록된 해시와 일치하는 `device_secret`. 기존 발급 고유번호 값과 순번은 변경하지 않음.
- `beagu_lv3_link_status_v1(p_user,p_visitor,p_actor)`: 현재 Lv2와 계정/작성자 매핑을 재검증하는 **향후 Lv3 검토 자격 신호**만 반환. **Lv3 권한을 부여하지 않는다.**

### 2. 실제 Auth 사용자와 세션을 재검증하는 Post-it Edge API

`supabase/functions/beagu-postit-api-v1/index.ts`

- `auth.getUser(jwt)`로 Auth 사용자 확인. 이메일 인증 및 비익명 계정만 허용.
- 인증서에서 서명으로 보호된 `session_id`를 추출하고, 16단계 `beagu_member_live_session_v1` 서비스 전용 RPC로 **현재 실제 사용자에 연결된 활성 Auth 세션인지 확인**. 로그아웃/세션 폐기·다른 계정의 세션 UUID로 계정 연결/포스트잇 작성 불가.
- 기존 `link_member` 버튼 요청은 **서버가 이미 검증한 Lv2 세션의 방문자 UUID**와 이전부터 유지된 고정 작성자 UID, 브라우저 원래 기기 비밀값만 사용. 클라이언트가 `auth_user_id`, 연결 대상 회원·작성자, Lv3 등급을 직접 정할 수 없음.
- 기존 포스트잇 `writer_status`에 `lv3LinkReady` boolean 추가. 기존 작성자 연결이 있다고 자동으로 Lv3 기반 기록이 완성되었다고 표시하지 않음.
- 기존 동적 PostgREST 필드 목록에서 strict Deno 파서 오류가 확인되어 `target()` 조회를 게시글/댓글별 명시적 최소 필드 SELECT로 교체. 조회 필드 확대 없이 TypeScript 검사를 통과.

### 3. 정식 승급을 오해하지 않게 하는 UI

- `js/beagu-account-status-v1.js`에 `lv3-link-ready` 상태 추가: **소유권 연결 확인 =/= Lv3 등급 부여**.
- `js/challenge-member-auth-v1.js`, `js/postit-account-v1.js`: 기존 계정 로그인 및 연결 버튼 재활용. 서버가 `lv3LinkReady:true`를 반환한 경우에만 소유권 연결 확인을 표시. 서버에서 실제 Lv3 권한이 생기기 전에는 Lv2로 유지.
- 신규 계정 생성 정책(신규 10자 이상 비밀번호)과 **기존 계정 짧은 비밀번호 로그인 허용**, SMS 별도 동의, 개인정보 요청·철회 UI는 계속 유지.

## 남은 안전 조건

1. **4단계 DB 암호화 백업 + 독립 복구 검증** 미완료. 5단계 실제 Auth URL 허용 설정 및 시험/운영 분리 점검 미완료.
2. 17단계의 **2026 본인 원본 설문 응답과 방문자 코드 간 신뢰할 수 있는 연결**이 아직 Google Forms와 실제 연결되지 않음. 이 연결이 없으면 기존 정상 Lv2 코드도 검증 불가가 될 수 있어 SQL/Edge를 운영 DB에 먼저 배포할 수 없음.
3. 구형 고유번호 보유자 중 **원래 기기 claim을 최초로 등록하지 못한 계정**은 기기 인증을 자동으로 보장할 수 없음. 기존 번호를 알고 최초 device claim을 등록할 수 있는 설계 특성도 있으므로, 이 경우 최초 claim 기록만 믿고 과거 소유권을 확정하지 말고 안전한 추가 복구·별도 소유권 확인 경로가 필요. 도용 방지 테스트는 이미 정상적으로 결합된 원기기 claim에 대해 수행했으며, **레거시 코드 전량의 실소유권을 증명한 것은 아님**.
4. 실제 계정의 구 연결 기록과 18단계 신규 독점 연결 기록이 일치하는지 읽기 전용으로 점검하고, 이관 시 충돌·중복·계정 삭제 정책을 승인해야 함.
5. 실제 **Lv3 자격·등급 발급·신규 최신 학교정보 열람**은 이번 단계에서 전혀 적용하지 않음. 후속 단계에서 별도 서버 인가/검증/최고 관리자 승인/롤백 설계 필요.
6. 운영 또는 공용 시험 웹 배포, 운영/시험 DB 마이그레이션, 실제 Auth 사용자 수정/메일 발송을 모두 금지한 상태 유지.

**18단계 결과:** Lv2 기기 소유권 + Auth 사용자 결합을 위한 통제된 DB/Edge 기반을 만들고 독립 검증까지 완료했다. 이 자체가 실서비스의 Lv3 회원제 활성화는 아니다.
