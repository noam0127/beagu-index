# 포스트잇: 정식 계정 인증 연동 계약 (2026-11-20)

## 현 상태와 범위
- 운영 Supabase Auth 사용자 0명, 비공개 account_* 테이블 미설치.
- 최종 확정 회원 정책 v3: Lv0 계정 생성 → 공통 코드 검증으로 Lv1 → 해당 로그인 계정의 추천 설문 유효 참여로 Lv2.
- 이 브랜치는 포스트잇 API에서 **인증된 계정 JWT + 현재 서버 계정레벨** 확인을 위한 읽기 전용 브리지를 구현한다. 사용자를 생성하거나 레벨을 부여하지 않는다.
- **현재 운영 서비스/데이터베이스에는 새 계정 연동 기능을 출시하지 않는다.** 별도의 계정 개발·검증이 끝날 때까지 포스트잇 Lv2 쓰기는 기존처럼 차단된다.

## 구현된 서버 계약
1. 클라이언트가 정식 계정 로그인으로 획득한 짧은 수명의 access JWT만 `Authorization: Bearer ...`로 서버에 제출한다. UUID, 고유번호, 공통인증번호, `level=2` 표시로 본인 소유권을 주장하지 않는다.
2. 서버는 `supabase.auth.getUser(jwt)`를 호출하여 유효하고 이메일이 확인된 사용자 ID를 검증한다.
3. 서비스 역할만 실행할 수 있는 `beagu_postit_account_access_v1(auth_user_id)` RPC에서 현재 계정 Lv0/1/2와 정지 여부를 재평가한다. 계정이 없거나 RPC가 설치되지 않았으면 실패로 처리한다.
4. Lv1 이상 회원은 댓글 조회 가능. 기존 비회원 Lv1 공통코드 세션도 댓글 열람은 유지한다.
5. Lv2 회원 중 **서버가 확인한 추천 승급 완료 시각**이 있는 계정만 게시글·댓글 작성, 좋아요, 신고, 본인 글 삭제 가능하다. 구 Lv2 공유코드 세션은 작성권한이 아니다.
6. DB의 작성자 UUID는 `HMAC(service_role_secret, "postit:auth-user:"+auth_user_id)`에서 서버가 결정하여 원래 Auth UUID를 공개·직접 저장하지 않는다. 비밀번호 변경·JWT 재발급·기기 변경 후에도 동일하다.
7. account level 변조·취소·탈퇴·미인증 계정·만료 JWT·RPC 부재는 모두 403, 인증 실패를 데이터 노출로 바꾸지 않는다.

## 설치 순서
1. Auth 계정/이메일 확인/CAPTCHA/복구/탈퇴 및 v3 비공개 계정·레벨·추천 원장, 강한 권한검사를 독립 테스트 Supabase에서 구현.
2. 정식 `account_profiles` + `account_level_profiles` 테이블과 lv1_verified_at, lv2_upgraded_at의 **신뢰된 서버 기록만 갱신**되는지 검증. 브라우저의 직접 INSERT/UPDATE 및 임의 RPC가 이 값을 변경하지 못해야 함.
3. 위의 서버 검증이 성공한 프로젝트에만 `20261120_beagu_postit_verified_account_bridge_v1.sql`을 적용하고, `anon`/`authenticated`는 RPC 실행 불가, `service_role`만 실행 가능함을 검증.
4. 정식 계정 UI에서 동일한 메모리 내 Auth 세션의 Authorization을 Post-it API에 전달. access token을 URL/localStorage/로그/분석 이벤트에 남기지 않는다. (현재 `js/beagu-account-client-v1.js`는 브랜치에만 존재하며 새 포스트잇 브리지와 연결되지 않음.)
5. 같은 계정의 새 기기 로그인·재로그인·탈퇴/정지 후 소유권·신고·좋아요 제한 등 실제 Lv1/Lv2 E2E 검증. 같은 권한 코드만 다른 계정에 입력해도 타인 글 삭제 불가 확인.
6. 기존 공개 페이지·학교검색·게임·비공개 설문 집계·관리자 예외처리 회귀 테스트 뒤, 별도 운영 배포 승인.

## 실패·오용 시나리오 (반드시 테스트)
- Auth JWT 미첨부/위조/만료/다른 프로젝트 → 403
- 이메일 미확인 → 403
- Auth 사용자 존재하지만 account level 0 → 작성 403, 댓글 403(별도 Lv1 비회원 세션이 없다면)
- Lv1 계정 → 댓글 200, 작성 403
- Lv2 계정에서 추천 승인 시각 없음 → 작성 403
- 정지/탈퇴 계정 → 403, 기존 행 작성자 변경 없음
- Lv2 계정에서 비밀번호 재설정·새 JWT·다른 기기 로그인 → 동일 HMAC 작성자 UUID
- 타인 UUID 또는 챌린지 번호만 제출 → 작성 403
- RPC 미설치/테이블 미설치 → 작성 403, 기존 Lv0 게시글·Lv1 세션 댓글 조회 유지
- 다른 account의 JWT로 다른 작성자의 글 `remove` → 403

## 별도 이슈
- 계정 정지/탈퇴와 이미 발급된 Auth access JWT의 수명·세션 철회 정책을 검증. 필요 시 Auth sessions.id 유효성 검사 및 짧은 JWT TTL 적용.
- 현행 인증코드 기반 Lv2 세션을 Auth 회원으로 간주하거나 운영의 `identity_visitor_id`를 임의 채우지 않는다.
- Supabase Auth 계정 신규 구축은 이 PR의 범위가 아니다. 테스트 환경이 현재 계정 v3와 일치하지 않는다면 API나 SQL을 강제로 배포하지 않는다.
