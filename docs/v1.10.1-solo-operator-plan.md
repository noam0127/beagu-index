## 최소 출시 경로 (순차)
1. 읽기 전용 운영 범위 재확인: 현재 운영 SHA/큐, 10종 inventory 및 managed Supabase 복구 가능 범위, 운영 DB·스토리지·외부 스크립트의 복구 누락 확인. 기존 조사 재사용. 비밀·개인정보는 공개 저장소에 기록하지 않는다.
2. 운영 백업 준비: 실제 exporter의 제한된 읽기 권한/일관성, 장기 복구 가능 암호화 키, private 저장소, 복원 호환 환경 및 용량, 보존/복구 목표. 자동화 실행 위치와 credential custody를 먼저 선택한다. Drive owner-only는 삭제 불가 저장소가 아님을 표시하고 별도 복구 가능한 복사본 또는 동등한 공급자 복구 보호를 검토한다. 현재 합성용 키 폐기 방식은 운영 백업에 사용하지 않는다.
3. 자동 백업·검증 실행기: 고정 코드와 신뢰된 실행 환경에서 백업 생성, 암호화, 원격 readback, 새 격리 대상 복원 및 source/restore fingerprint 검증. 성공 여부를 운영자가 입력한 true 값으로 대신하지 않는다. 운영 데이터가 포함된 테스트는 별도 승인과 private 환경 없이는 실행하지 않는다.
4. 단일 승인과 제어 ledger: 기존 owner MFA, exact job/base/candidate/plan/recipe pin, 짧은 승인 유효기간, 원자적 일회성 claim과 내구적 상태/증거 기록. 실패·불확실 효과 이후 자동 재시도 금지. 외부 보호된 기록 또는 공급자 감사 증거가 없으면 rollback protection을 주장하지 않는다. 별도 사람은 요구하지 않지만 자동 검증 키/권한은 배포 후보 및 브라우저와 분리한다.
5. 물길 선행 확인: 기존 7개 확인 항목(telemetry SQL, admin status SQL, ingest Edge, review Edge, Apps Script source, authenticated sync, unchanged publication gates)을 실제 읽기 관측으로 검증. 누락 설치는 별도 승인된 고정 절차로 처리. Pages 포인터만으로 완료를 추론하지 않는다.
6. 통합 실행/검수: 기존 backup→SQL/scheduler→Edge→backend verify→Pages→live verify 순서와 복구 중단 규칙 보존. 신뢰된 worker 및 provider 연결을 격리 검증하고 단일 게시자만 사용한다. 부트스트랩 자체는 별도 승인 필요.
7. 관리자 업데이트 센터 등록: 코드/통합 검증과 운영 준비 증거 확인 후 등록. 등록과 운영 적용은 별도. 실제 적용은 본인 승인 전 금지.

- 출시와 무관한 독립 기관형 서명/관측자 구축은 후순위. 실제 백업·복원 및 안전한 단일 승인 자동화가 우선이다.

## 1인 운영형 자동 백업 후보 1차
- 고정 생성 합성 PG17만 대상으로 snapshot capture → 기존 스트리밍 AEAD → private 로컬 모의 원격 저장 → 별도 저장소 readback 및 SHA256 → 장기 보관용 테스트 키 재개봉 → 별도 네트워크 차단 PG17 컨테이너 복원 및 fingerprint 비교를 자동 연결. 실제 Drive 재업로드/운영 DB 연결 없음. 합성 대용량 성공 기록은 기존 증거로 재사용한다.
- 작업별 no-replace attempt/manifest/complete 기록, 동일 job 재시도 금지, 외부 manifest digest, 키·저장소·ledger 경로 분리 및 잘못된 키/암호문 변조/누락 검사. 완료 기록은 원본 fingerprint 재확인 이후에만 작성. 재시작 후 보존 키로 복원 테스트. 로컬 모의 저장소는 원격 내구성 또는 삭제 방지의 증거가 아니다.
- 테스트용 작은 dump는 기존 128MiB 메모리 제한을 사용한다. 운영용 exporter, 전체 Supabase 관리 범위 복원, 실제 장기 키 custody, 원격 보존 및 실행 환경은 아직 미연결. 운영 데이터/실제 백업 금지, production_backup_proof=false, execution_enabled=false 유지. 별도 인간 관측자는 필수 출시 경로에서 제외한다.

## 1인 운영형 연결 준비 및 관리자 승인 전 화면
- 기존 owner active MFA와 productionAdmin 단일 승인/원자적 create 경로를 재사용할 예정이다. inspect_integrated_plan의 solo_preparation은 server-derived SHA 및 recipe 존재 여부, 미연결 항목만 반환한다. UI는 승인 전임을 표시하고 실행 버튼 잠금을 유지한다. 입력 approved/execution_enabled 등은 무시한다. 실제 create 연동, 신규 승인 저장/만료 처리, 자동 백업 gate 연결은 아직 수행하지 않는다.
- 고정 read-only inventory SQL은 PostgreSQL 17 카탈로그/스키마·관계 수 등만 조회하고 실제 운영에서는 실행하지 않았다. 계정/예약 작업/스토리지/외부 의존성과 Supabase 관리 범위의 상세 복원 방법은 별도 확인이 필요하다. 연결 정책 후보는 10종 복구 방법 및 근거 pin, private worker/Drive/복구 사본, 보존/RPO/RTO/용량/key ID를 검사한다. 운영 수치·환경·자격증명은 아직 미확정이며 실제 연결 성공으로 간주하지 않는다.
- 기존 합성 성공 기록 재사용, 운영 DB/Drive 쓰기/배포/Vercel/Mac 작업 없음. CI는 격리 PG17 및 모의 관리자 API만 사용.

## 최소 연결 조건 및 기존 승인-백업 실행 통합
- 출시 필수 연결 조건을 5가지로 한정: (1) 신뢰된 private worker 및 제한된 read-only 운영 exporter, (2) 실제 Supabase 관리 범위/외부 자산의 복원 경로, (3) 기존 비공개 Drive와 복구 가능 별도 사본, 보존된 key 및 암호화 임시 공간, (4) 본인의 MFA 단일 승인과 exact job/plan/recipe, 내구적 claim 기록, (5) 실제 백업 readback/격리 복원 및 물길 선행 관측. 독립 인간 관측자 별도 채용 및 추가 서명 개발 제외.
- 초기 운영 정책 제안(미승인): 업데이트 직전 백업, 평상시 일일 백업(RPO 목표 24h), RTO 목표 4h, 보존 30일, 운영자 관리 복구키 별도 복구 사본. 공급자 보존/요금·실제 용량·작업 환경은 확인 후 확정. 어떠한 운영 설정에도 적용하지 않았다.
- 기존 FixtureRunner/Ledger 승인·claim 흐름에서 동일한 격리 PG17 source를 백업하고 별도 PG17 복원 검증하는 첫 단계 adapter를 연결했다. 승인된 변경이 실행될 정확한 source의 fingerprint를 manifest에 기록하며, 키 누락 시 첫 단계 blocked 및 다음 SQL/Pages 미실행을 테스트한다. 기존 합성 Drive 증거 재사용; 로컬 모의 저장소만 사용한다. 실제 관리자 Edge create/production worker/운영 exporter는 연결되지 않았고, 운영 잠금 유지.
